## 0. 요약 — 3판의 결론

1. **배포본은 소스에서 바이트 단위로 재현됩니다.** `src/`로 빌드한 14개 파일이 배포된 `PM_APP`과 **전부 동일**합니다. 이것은 두 가지를 뜻합니다 — 받은 소스가 배포본의 진짜 원본이고, **수정 대상이 정확히 확정되었다**는 것입니다. 2판의 최우선 결함 A는 **해소**되었습니다.

2. **테스트 37개를 전부 돌렸고 35개가 통과했습니다.** 실패 2건은 둘 다 제품 결함이 아닙니다 — `test_demo`는 빌드 산출물이 없어서였고(생성 후 통과 확인), `test_interop`은 **매니페스트가 가리키는 파일 중 일부가 없다**는 검사만 실패했습니다. 즉 **프로젝트 자체 테스트가 제 D-7 지적을 독립적으로 확인**해 줍니다.

3. **미해결이던 점검 포인트를 모두 닫았습니다.** 아키텍처 경계 검사 통과, **규모 요구(100 프로젝트 / 1,000명 / 8,000 배정)에서 8.8초 로드·오류 0건으로 충족**, 악성 워크북 XSS 실험에서 **실행 0건**, 감사 CSV에 **엑셀 수식 주입 방어까지 구현**되어 있음을 확인했습니다.

4. **그러나 핵심 결함 3건은 소스에서 확정되었고, 하나는 실제로 재현했습니다.** 공유 폴더에 PM_APP 두 개를 띄워, **A가 저장한 프로젝트 9건이 B의 저장으로 경고 한 줄 없이 사라지는 것**을 재현했습니다. 저장 응답은 `{"ok": true}`였습니다. 그리고 세 공백은 **Electron 셸에도 동일하게 존재**합니다 — 포팅 누락이 아니라 양쪽 다 만들지 않은 것입니다.

5. **요청하신 레코드 단위 잠금은 여전히 구조 변경입니다.** 스펙이 N-20에서 *"다른 제품이고, 저장 형식이 갖고 있지 않은 병합 모델을 필요로 한다"* 고 명시합니다. 4·5부의 서버 전환 설계가 그 답이며, **0단계가 짧아져 전체 일정이 약 2.5~3개월로 줄었습니다.**

### 2.5 감사 로그 — 수식 주입 방어까지 구현되어 있습니다

`core/06c_audit.js`의 CSV 필드 처리입니다.

```javascript
function csvField(v){
  if (v === null || v === undefined) return "";
  let s = v instanceof Date ? v.toISOString() : String(v);
  if (/^[=+\-@]/.test(s)) s = "'" + s;                       // ← 수식 주입 방어
  return /[",\n\r]/.test(s) ? '"' + s.replace(/"/g, '""') + '"' : s;
}
```

주석이 이유를 씁니다 — *"`=`, `+`, `-`, `@`로 시작하는 셀은 엑셀에게 **수식**이고, 이 파일은 정의상 엑셀에서 열린다. `=SUM(A1)`이라고 적은 프로젝트 메모는 **텍스트로 도착해야 하고 스프레드시트가 평가해서는 안 된다.**"*

**대부분의 개발자가 빠뜨리는 방어입니다.** 이에 따라 2판의 결함 G를 **내용 안전성 문제에서 SMB 동시 이어쓰기 문제로 축소**합니다.

### 🔴 결함 C. 복구 기록 미구현 — NR-STO-07 미이행

### D-10 — 가이드의 공식이 실제 계산과 다릅니다

이것은 **"다른 Claude에게 전달한다"는 원래 질문에 직결되는 결함**입니다.

가이드 §5.1이 제시하는 공식:

```
monthly_load_fte = period_weight × role_factor × person_weight × month_coverage
```

실제 구현(`src/core/06_calculate.js`)은 **2패스 정규화**입니다.

```javascript
const stdF  = stdMonthly(proj, seg ? seg.period_name : null);   // ← standard_fte
const claim = (rf / share) * personWeight(a, y, m) * cov;
/* 이 사람의 '몫 주장'일 뿐, 아직 그의 수치가 아니다. 다른 사람들 것과
   함께 정규화하는 일은 프로젝트-월 전체가 정해진 뒤 두 번째 패스에서 일어난다 */
```

주석이 원칙을 밝힙니다(REQ-CAL-19, R-32 개정) — *"표준(standard)이 그 달의 수요이고, 프로젝트 자신의 기간 가중치가 이 연구에 맞게 올리거나 내린다. 역할 인자는 그 수요를 **실제로 배치된 역할들 사이에 나눈다**. 그래서 **몫의 합이 1이 되고, 몇 명이 붙든 프로젝트-월은 표준과 같아진다.**"*

**차이가 두 가지입니다.**

| | 가이드 §5.1 | 실제 구현 |
|---|---|---|
| `standard_fte` | **공식에 없음** | 프로젝트-월 총량을 결정하는 항 |
| 사람 간 관계 | 각 배정을 **독립적으로** 곱셈 | 몫을 **정규화**해 합이 1 (REQ-CAL-19) |

§5.2의 예제 계산(`1.20 × 0.90 × 0.40 × 0.7097 = 0.3066 FTE`)도 같은 공식을 씁니다. **가이드만 읽고 숫자를 재계산하는 AI나 사람은 앱과 다른 값을 얻습니다.**

**완화 요소**: 가이드 §9.3이 *"공식을 직접 다시 도출하지 말고 `calculate`를 쓰라 — 그래야 당신의 답과 대시보드가 어긋날 수 없다"* 고 지시하며, §3.1의 `PeriodFTEStandard` 설명은 *"`standard_fte`가 크기를 담고 `ProjectPeriod.weight`는 조정한다"* 고 올바르게 씁니다. **즉 가이드는 스스로 알고 있고, §5.1의 한 줄 공식만 그 사실을 반영하지 않았습니다.** 그래도 §5.1은 사실로 단정되어 있어 고쳐야 합니다.

### 5.5 요청 b) 레코드 단위 잠금 설계

잠금 단위 2종 — **프로젝트 잠금**(프로젝트 행 + 마일스톤·기간·월별추정 + **그 프로젝트의 모든 배정**)과 **배정 잠금**(배정 1행 + 가중치 창 + 월별추정). 부모 프로젝트에 **의도 표시(intent)** 를 남기고, `UNIQUE (scope, record_id, mode)` 제약으로 **DB가 승자를 판정**하는 **다중 단위 잠금(multi-granularity locking)** 설계입니다.

> **왜 프로젝트 잠금이 배정까지 포함해야 하는가.** 프로젝트 기간은 **건물의 층 구분선**이고 배정은 **각 층의 사무실**입니다. 층 구분선을 옮기면 **모든 사무실의 위치가 함께 바뀝니다.**

**3판에서 소스로 확인한 근거**: `src/core/06_calculate.js`는 프로젝트-월 총량을 `standard_fte × period_weight × coverage`로 잡고 **그 안에서 사람들의 몫을 정규화**합니다(REQ-CAL-19). 따라서 기간 경계를 바꾸면 **그 프로젝트 모든 배정의 수치가 동시에 재계산**되며, 배정을 하나만 바꿔도 **같은 역할을 가진 다른 사람의 몫까지 바뀝니다**(`rf / share`). 즉 프로젝트 잠금이 하위 배정을 포함해야 하는 이유가 **가중치 곱셈보다 강한 결합** 때문임이 확인되었습니다.

| # | 요청 | 현재 잠금 | 결과 | 메시지 |
|---|---|---|---|---|
| 1 | A가 `PRJ-001` 기간 수정 | 없음 | ✅ 허용 | "PRJ-001을 편집 중입니다" |
| 2 | **B가 `PRJ-001` 기간/월 FTE 수정** | A가 PRJ-001 | ❌ **차단** | **"김OO(DM팀)이 PRJ-001을 편집 중입니다. 11:31 시작, 활동 중."** ← 요청 예시 1 |
| 3 | B가 `ASG-007` 수정 | A가 PRJ-001 | ❌ 차단 | "김OO이 PRJ-001 전체를 편집 중" |
| 4 | B가 `ASG-007` 수정 | 없음 | ✅ 허용 | PRJ-001에 의도 표시 |
| 5 | **C가 같은 `ASG-007` 수정** | B가 ASG-007 | ❌ **차단** | **"이OO(DM팀)이 이 배정을 편집 중입니다"** ← 요청 예시 2 |
| 6 | C가 **다른** `ASG-009` 수정 | B가 ASG-007 | ✅ 허용 | — **진짜 동시 편집 지점** |
| 7 | A가 `PRJ-001` 전체 수정 | B가 ASG-007 | ❌ 차단 | "이OO이 이 프로젝트의 배정을 편집 중" |
| 8 | D가 `PRJ-002` 수정 | 위 전부 | ✅ 허용 | — 완전 독립 |

**잠금 규칙은 기존 사상을 계승합니다** — 값이 실제로 바뀔 때 획득(NR-STO-10), 30초 생존신호 / 30분 만료 분리(NR-STO-14), 자기 세션 즉시 복구(NR-STO-19), 실명+부서+시작시각+해제예정 메시지(NR-STO-12). **이 사상은 80개 테스트로 검증되었으므로 새로 발명할 것이 없습니다.**

**결함 D 재발 방지 3중 장치**: ① 다른 레코드로 이동 시 이전 잠금 필수 해제 ② `expires_at` 자동 만료 ③ **관리자용 "현재 잠금 목록" + 강제 해제**(현재 전혀 없는 수단).

**놓치기 쉬운 문제 — "사람" 축 충돌.** 한 인원의 서로 다른 배정을 두 사람이 각각 정당하게 수정하면 그 인원의 월 합계가 과다배정에 접근하는데 **둘 다 자기 화면에서는 볼 수 없습니다.** 잠금이 아니라 **알려주기로** 풀어야 합니다 — 저장 시 해당 인원 전체 합계 재계산 후 경고(막지 않음), 같은 인원의 다른 배정 편집 중이면 정보성 안내, 과다배정 목록 상시 노출.

### 5.6 요청 a) 관리자 권한 분리

권한 3단계: **관리자**(전부 + General assumptions 수정 + 사용자·권한 관리 + 잠금 강제해제) / **편집자**(업무 데이터 편집, 가정값 읽기만) / **조회자**(읽기·내보내기만).

**General assumptions = 4개 테이블**: `PeriodFTEStandard`(88행) · `RoleFactor`(430행) · `Lists` · `Config`. 실측에서 이 탭이 **98~184행**을 렌더링하는 것을 확인했습니다.

> **비유**: 이 4개는 **환율표**입니다. 개별 프로젝트 데이터가 "금액"이라면 이것은 환산 환율입니다. **한 칸 바꾸면 회사 모든 장부의 숫자가 동시에 바뀝니다.**

3판에서 소스로 확인한 사실이 이 판단을 강화합니다 — `PeriodFTEStandard.standard_fte`는 **프로젝트-월 총량 자체**를 결정하는 값입니다(REQ-CAL-19). 가중치 하나가 아니라 **분모**입니다.

**가정값은 잠금이 아니라 버전으로**: 새 버전 저장(덮어쓰지 않음) → 적용 전 **영향 범위 표시**("프로젝트 62개, 인원 20명의 FTE가 바뀝니다. 새로 과다배정 3명: …") → 편집 중 사용자에게 알림 → 과거 버전 보존으로 "지난달 보고서는 어느 기준이었나"에 답변 가능.

**권한 확인은 반드시 서버에서** — 화면 버튼 숨김은 친절함이지 보안이 아닙니다.
