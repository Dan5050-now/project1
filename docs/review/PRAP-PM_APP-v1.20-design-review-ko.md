## 0. 요약 — 세 문장

1. **프로그램 자체의 완성도는 높습니다.** 코드가 깔끔하고, 모든 판단에 "왜 이렇게 했는지"가 주석으로 남아 있고, 데이터가 깨지지 않게 저장하는 절차(원자적 저장)가 제대로 구현되어 있습니다. 1인용 도구로서는 상용 제품 수준입니다.

2. **그러나 "여러 명이 동시에 편집"은 이 프로그램의 설계 범위 밖입니다.** 이것은 제 추측이 아니고, 개발계획서 v2.54가 스스로 명시한 사실입니다. `02_Scope` 시트의 **Out of scope**에 *"Multi-user concurrent editing, or any server / database component"* 와 *"Authentication, user accounts, permissions"* 가 확정(Confirmed Q-12) 상태로 적혀 있고, 가정 **A-06**은 *"한 번에 한 사람만 워크북을 관리한다 — 조정할 동시 편집은 없다"* 입니다.

3. **따라서 요청하신 a) 동시 편집 + 관리자 권한 분리, b) 레코드 단위 잠금은 "기능 추가"가 아니라 "구조 변경"입니다.** 중앙 서버 + 데이터베이스로 다시 만드는 것이 맞고, 다행히 **버릴 것은 거의 없습니다** — 값비싼 자산인 계산 로직과 화면은 그대로 재사용할 수 있습니다.

## 1부. 이 프로그램은 어떤 구조인가 (비전문가용 설명)

### 1.1 겉모습과 실제가 다릅니다

이 프로그램은 **브라우저(엣지/크롬)에서 열리는 웹 화면**입니다. 그래서 "웹 서비스"처럼 보입니다. 하지만 실제 구조는 전혀 다릅니다.

> **비유: "웹사이트"가 아니라 "혼자 쓰는 계산기 자판기"입니다.**
>
> 보통의 사내 웹 시스템은 **식당 한 곳**과 같습니다. 주방(서버)이 하나 있고, 손님 열 명이 각자 자리에서 주문하면 주방이 순서를 정리해서 요리를 내줍니다. 누가 무엇을 주문했는지 주방이 다 알고 있으니 충돌을 조정할 수 있습니다.
>
> 이 프로그램은 **자판기 열 대**입니다. 사람마다 자기 PC에 자판기가 한 대씩 놓입니다. 자판기끼리는 서로 대화하지 않습니다. 다만 **재료 창고(공유 폴더)를 같이 씁니다.** 조율하는 주방장이 없고, 창고에 "지금 이 재료 쓰는 중" 이라고 쪽지를 붙여두는 것이 유일한 조정 수단입니다.

기술적으로 풀면 이렇습니다.

```
[ 사용자 A의 PC ]                        [ 사내 공유 폴더 (\\server\share) ]
  PM_APP.py 실행
    └ 파이썬 프로세스 1개                    PM_APP\              ← 프로그램 파일
        └ 127.0.0.1 (자기 PC 안에서만)          PM_APP.py
            통하는 작은 웹 서버                 pmapp\
                └ 브라우저에 index.html          app\index.html
                  (683KB, 한 장)                data\users\<계정>\   ← 데이터
                                                  workspaces\*.prap
[ 사용자 B의 PC ]                                 backups\
  똑같은 것이 따로 하나 더 뜸                   data\audit\*.csv     ← 변경 이력
```

핵심은 **"서버 1대에 여러 명이 접속"이 아니라 "사람 수만큼 서버가 각자의 PC에 뜬다"** 는 점입니다. `127.0.0.1`은 "내 PC 자신"을 가리키는 주소이고, 코드에도 *"이 기계에서만 접근 가능(this machine only)"* 이라고 명시되어 있습니다. 옆자리 동료의 PC에서는 이 주소로 접속할 수 없습니다.

### 1.3 잘 만들어진 점 — 칭찬해야 하는 부분

솔직히 말해 **이 코드는 "AI가 뚝딱 만든 것" 수준을 확실히 넘습니다.** 근거를 들면:

**① 데이터를 절대 잃지 않는 저장 절차 (`workspace.py`)**

파일을 저장할 때 대충 덮어쓰지 않습니다. 5단계를 거칩니다.

```
① 새 내용을 임시 파일(.tmp-1234)에 쓴다
② fsync — 디스크에 물리적으로 확실히 기록한다 (캐시에만 있으면 정전 시 사라짐)
③ 기존 파일을 backups\ 로 복사해둔다
④ os.replace — 임시 파일을 진짜 파일로 "한 순간에" 바꿔치기한다
⑤ 미저장 메모(journal)를 지운다
```

> **비유**: 계약서를 고칠 때 원본에 볼펜으로 덧쓰지 않고, **새 종이에 전부 다시 쓴 다음 원본과 한 번에 맞바꾸는** 방식입니다. 맞바꾸는 순간은 쪼갤 수 없으므로, 정전이 나도 "옛 계약서" 아니면 "새 계약서"이고 **반쪽짜리는 절대 나오지 않습니다.**

윈도우 환경 고려도 정확합니다. 코드 주석에 *"`os.rename`이 아니라 `os.replace`. 윈도우에서는 기존 파일 위로 rename이 실패한다"* 고 적혀 있습니다. 이것은 윈도우에서 실제로 사고가 나는 지점이고, 제대로 짚었습니다.

**② 오류 메시지가 사람의 말입니다**

보통 프로그램은 `Error: EACCES`처럼 씁니다. 이 프로그램은 이렇게 씁니다.

| 상황 | 실제 메시지 (번역) |
|---|---|
| 디스크 공간 부족 | "저장할 공간이 부족합니다. **아무것도 변경되지 않았고 이전 저장본은 온전합니다.**" |
| 권한 없음 | "이 폴더에 쓸 수 없습니다. 다른 곳에 '다른 이름으로 저장' 하거나 쓰기 권한을 요청하세요." |
| 회사 보안으로 암호화된 파일 | "파일 보안으로 보호된 것 같습니다. **엑셀에서 먼저 열어 잠금을 푼 뒤** 다시 가져오세요." |
| 남이 편집 중 | "**김OO (DM팀)** 이 이 계획을 편집 중입니다. 11:31에 시작했고 현재 활동 중입니다." |

마지막 항목이 특히 좋습니다. `claim.py`의 주석이 이유를 직접 밝힙니다 — *"누군가의 이름을 말하고 언제 풀리는지 알려주는 메시지는 행동으로 옮길 수 있지만, '파일이 사용 중입니다'는 그렇지 않다."* 이것은 사용자를 실제로 배려한 설계입니다.

또 **"손상된 파일"과 "보안으로 암호화된 파일"을 구분**합니다(`looks_protected`). 둘은 프로그램 입장에서 똑같이 "읽을 수 없는 바이트"인데, 이를 구분하지 못하면 사용자가 있지도 않은 백업을 찾아 헤매게 됩니다. 30초면 풀 수 있는 문제를 반나절 문제로 만들지 않으려는 배려입니다.

**③ 시각 표기를 한 곳에서 통제 (`timefmt.py`)**

이 파일은 **이 코드베이스에서 가장 인상적인 부분**입니다. 파일 20줄짜리인데, 이유가 이렇게 적혀 있습니다.

> Electron(예전 버전)은 자바스크립트 방식 `2026-08-18T09:41:07.412Z`로 시간을 적고, 파이썬은 `2026-08-18T09:41:07.412000+00:00`로 적는다. 같은 순간, 다른 표기다. 공유 폴더의 계획 파일을 두 버전이 번갈아 건드리는 날이 오면 **이 차이가 전부가 된다**: 해석 불가능한 시각은 "1970년"으로 읽히고, 1970년은 만료된 것이고, 만료는 **지금 편집 중인 계획을 남에게 넘겨주는 것**이다.

이것은 실제로 데이터를 날려먹는 시나리오이고, 그걸 미리 발견해 한 파일에 격리했습니다. 이 수준의 예측은 경험 있는 개발자의 것입니다.

**④ 잠금을 "파일 열 때"가 아니라 "값이 바뀔 때" 잡습니다**

`index.html`이 `beginEditSession`(값이 바뀌려는 순간)을 가로채서 그때 잠금을 요청합니다. 주석의 이유: *"열 때 잠금을 잡으면, 계획을 잠깐 보다가 점심 먹으러 간 사람이 30분간 팀 전체를 막게 된다."*

**⑤ 자물쇠를 "파일 배타 생성"으로 구현했습니다**

```python
fd = os.open(lock_path(ref), os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o644)
```

주석이 이유를 정확히 씁니다 — *"읽고-나서-쓰기가 아니다. 두 세션이 동시에 '비어있음'을 읽고 둘 다 쓸 수 있으며, 각자 자기가 이겼다고 믿게 된다. 배타적 생성은 파일시스템이 판정하고, 승자가 정확히 한 명이며, **SMB(윈도우 공유 폴더)에서도 동작한다.**"*

이것이 동시성 프로그래밍의 정석입니다. **네트워크 공유 폴더에서 유일하게 신뢰할 수 있는 원시적 잠금 수단**을 골랐습니다.

**⑥ 30초와 30분을 분리했습니다**

| 값 | 의미 |
|---|---|
| 30초 (`HEARTBEAT_MS`) | "이 사람 아직 살아 있나?" |
| 30분 (`EXPIRY_MS`) | "다른 사람이 가져가도 되나?" |

덕분에 *"말하던 중인 동료"* 와 *"20분 전에 노트북이 죽은 동료"* 를 구분해서 안내할 수 있습니다. 두 값을 하나로 합쳤다면 불가능한 구분입니다.

### 1.4 설계 문서 자체에 대한 평가

개발계획서 v2.54와 프로그래밍 스펙 v1.28은 **품질이 상당히 높습니다.**

- **28개 질문 전부에 답이 달려 있고, 각 답이 어떤 요구사항/검증규칙으로 반영됐는지 추적됩니다.** (`11_Open_Questions`)
- **12개 위험(R-01~R-12)에 발생가능성·영향도·완화책이 붙어 있고**, 검토를 거쳐 등급이 오르내린 이력이 남아 있습니다.
- **검증 규칙 36개(V-00~V-35)** 가 심각도(fatal/error/warning/information)별로 분류되어 있습니다. 이 정도 밀도의 데이터 검증은 사내 도구로서는 과할 정도로 꼼꼼합니다.
- **은퇴한 규칙도 남겨뒀습니다** (V-25, V-28 = RETIRED). 왜 없앴는지가 기록되므로 나중에 같은 논쟁을 반복하지 않습니다.

**다만 설계 문서에서 지적할 점이 있습니다.**

| # | 지적 | 설명 |
|---|---|---|
| D-1 | **파이썬 버전의 설계서가 없습니다** | 코드 7개 파일 전부가 `PRAP_NewApp_Specification_v1.3.xlsx`를 참조하는데, **이 파일이 첨부되어 있지 않습니다.** 제공된 스펙 v1.28은 HTML 앱(계산·검증·화면)의 스펙이고, 파이썬 껍데기(서버·잠금·저장)의 스펙은 다른 문서입니다. 즉 **지금 검토 중인 코드의 설계서를 우리가 갖고 있지 않습니다.** |
| D-2 | 개발계획서가 파이썬 버전을 반영하지 못했습니다 | 계획서 `07_Architecture`는 여전히 *"no install, no server"*, `REQ-NFR-04`는 *"no network calls"* 라고 씁니다. 그런데 파이썬 버전은 **소켓을 열어 HTTP 서버를 띄웁니다.** 코드는 이 모순을 알고 있고 `server.py` 상단에서 *"이것은 NR-SEC-01로부터의 이탈이다"* 라며 6가지 안전장치로 변론합니다. 변론은 타당하지만, **계획서가 갱신되지 않아 문서와 코드가 어긋난 상태입니다.** |
| D-3 | 규모 가정이 50배 바뀌었는데 검증 기록이 없습니다 | 초기 가정 A-01은 *"20개 프로젝트, 30명"* 이었는데, 변경요청 R-06으로 `REQ-NFR-03`이 **"100개 프로젝트, 1,000명, 배정 8,000건, 60개월"** 로 재설정되었습니다. 이는 최대 **1,000명 × 60개월 = 60,000칸**의 표입니다. 계획서는 "가상 스크롤로 처리한다"고 적었지만 **실제로 그 규모에서 측정한 기록은 문서에 없습니다.** 684KB 단일 HTML이 브라우저에서 60,000칸을 그리는 성능은 반드시 실측이 필요합니다. |
| D-4 | 스키마 버전이 코드 두 곳에서 다릅니다 | 화면(`index.html`)은 `SCHEMA_EXPECTED = 12`, 파이썬(`workspace.py`)은 `SCHEMA_EXPECTED = 5`. 계획 파일을 저장할 때 헤더에 **`schema_version: 5`가 찍힙니다.** 현재는 그 값을 아무도 다시 읽지 않아 사고가 나지 않지만, **언젠가 읽게 되는 날 잘못된 판단을 하게 되는 시한폭탄**입니다. |
| D-5 | 버전 번호가 두 개입니다 | `version.txt` = **1.20** (파이썬 껍데기), `index.html` 내부 `APP_VERSION` = **1.50** (화면). 가이드 문서는 *"app/PRAP.html v1.50"* 을 말하는데 zip 안 파일명은 `app/index.html`입니다. 사용자가 "몇 버전 쓰세요?"라는 질문에 답할 수 없습니다. |

## 2부. 지금 상태로 사내 공유 폴더 운영이 가능한가

### 2.1 배포하면 실제로 벌어지는 일

먼저 **좋은 소식**입니다. 실제로 띄워서 확인했고 정상 구동했습니다.

```
Project Management APP
  version      1.20
  application  .../PM_APP
  your data    .../PM_APP/data/users/root
  chosen by    3 - writable data\ beside the application
  listening    127.0.0.1:8765  (this machine only)
  file dialogs in the page (no tkinter here)
```

그리고 **파일 단위 잠금은 설계대로 정확히 작동했습니다.**

```
① B가 새 계획 저장 (잠금 없음)          → 성공
② A가 잠금 획득                          → 성공
③ B가 잠금 시도                          → 차단됨
   메시지: "UserA (DM) 이 이 계획을 편집 중입니다. 11:31에 시작, 현재 활동 중."
④ A가 잠금 보유 중 B의 저장 권한          → 없음 (올바르게 차단)
```

**여기까지는 훌륭합니다.** 하지만 아래 7가지가 실제 운영을 막습니다.

### 2.2 확인된 결함 — 실측 기준

#### 🔴 결함 1. 기본 설정에서는 **애초에 데이터 공유가 안 됩니다** (가장 중요)

데이터 폴더 결정 규칙(`paths.py`)이 사용자마다 **개인 폴더**를 만듭니다.

```
\\server\share\PM_APP\data\users\kim_ch\workspaces\   ← 김OO의 계획들
\\server\share\PM_APP\data\users\lee_sy\workspaces\   ← 이OO의 계획들
\\server\share\PM_APP\data\users\park_jh\workspaces\  ← 박OO의 계획들
```

실제로 띄웠을 때 생성된 폴더가 `data/users/root/workspaces` 였습니다. 그리고 파일 열기/저장 창의 기본 위치도 **자기 개인 폴더**입니다.

> **비유**: 공동 창고를 빌려놓고 안에 개인 사물함을 하나씩 나눠준 상태입니다. 사물함은 잘 작동하지만 **"우리 팀 공용 선반"이 없습니다.**

즉 **같은 계획 파일을 여러 명이 편집하는 상황 자체가 기본값으로는 발생하지 않습니다.** 공유하려면 매번 파일 탐색으로 남의 폴더 경로를 직접 찾아 들어가야 합니다. 잠금 기능이 잘 만들어져 있어도 **그 기능이 발동할 상황이 만들어지지 않습니다.**

**※ 이것은 버그가 아니라 의도된 설계입니다** — 코드 주석에 *"각자 자기 폴더를 갖고, 아무도 아무것도 묻지 않는다(NR-DEP-15)"* 라고 적혀 있습니다. 1인용 도구의 관점에서는 올바른 선택이지만, 요청하신 협업 용도와는 **정반대 방향**입니다.

#### 🔴 결함 2. 다른 계획으로 옮기면 **이전 계획 잠금이 풀리지 않습니다** (실측 확인)

```
잠금 A 획득  → 성공, 현재 파일 = planA.prap
잠금 B 획득  → 성공, 현재 파일 = planB.prap
A의 잠금 파일이 아직 남아 있는가?  → True   ← 문제
프로그램 종료 후 → A 잠김: True | B 잠김: False
```

원인을 코드에서 확인했습니다. `stop_heartbeat()`이 이렇게 되어 있습니다.

```python
def stop_heartbeat(self):
    self._heartbeat = None   # 스레드는 stop 이나 잠금 상실을 알아챈다
```

**변수만 비우고 실제 스레드는 멈추지 않습니다.** 그래서 planA의 심장박동 스레드가 계속 살아서 30초마다 planA 잠금을 갱신합니다. 게다가 종료 시 해제 대상은 "현재 파일" 하나뿐이라 planA는 그냥 남습니다.

> **결과**: 사용자가 계획 A를 잠깐 고치다가 계획 B로 옮겨 일하면, **계획 A는 그 사람이 프로그램을 끄고 나서도 30분간 다른 사람이 손댈 수 없습니다.** 프로그램을 계속 켜두면 **하루 종일 잠긴 상태로 남습니다.**

#### 🔴 결함 3. 남의 저장 내용을 조용히 덮어쓸 수 있습니다 (실측 확인)

```
A가 잠금 해제 후, B의 쓰기 권한      → True
save_workspace 안에 mtime/버전 확인이 있는가?  → 없음
```

시나리오를 풀면:

```
09:00  A가 계획을 열어 편집 시작 (잠금 획득)
09:05  B가 같은 계획을 열어 "보기만" 함 → 잠금 없음, B의 브라우저에 09:05 시점 데이터
09:30  A가 저장 → 파일에는 A의 작업이 들어감
09:35  A가 프로그램 종료 → 잠금 해제
09:40  B가 한 칸을 수정 → 잠금 획득 성공 (아무도 안 갖고 있으니)
09:41  B가 저장 → B의 브라우저에 있던 09:05 데이터가 파일 전체를 덮어씀
       ⚠ A의 09:00~09:30 작업이 경고 한 줄 없이 사라짐
```

> **비유**: 두 사람이 같은 문서를 인쇄해 가져갔습니다. A가 고쳐서 원본을 갱신했습니다. B는 **자기가 들고 있는 옛 인쇄물을** 고쳐서 원본 자리에 놓았습니다. A의 수정은 사라졌고, **아무도 그것을 알아채지 못합니다.**

방지 방법은 표준적이고 간단합니다 — 저장 직전에 "내가 읽은 이후 파일이 바뀌었나?"를 확인하는 것입니다. 그리고 **그 확인용 기능(`ws/stat`)이 서버에 이미 만들어져 있습니다.** 그런데 아무도 호출하지 않습니다(아래 결함 4).

#### 🔴 결함 4. 서버 기능 3개가 **만들어졌지만 아무도 호출하지 않습니다**

화면이 실제로 호출하는 기능을 전수 조사한 결과입니다.

| 서버가 제공하는 기능 | 화면이 호출? | 결과 |
|---|---|---|
| `journal/read` (미저장 내용 읽기) | ✅ 호출 | — |
| **`journal/write`** (미저장 내용 기록) | ❌ **0회** | **읽을 내용이 애초에 기록되지 않음 → 복구 기능이 항상 "없음"** |
| **`ws/stat`** (파일 변경 확인) | ❌ **0회** | **결함 3을 막을 수 있었는데 쓰이지 않음** |
| **`claim/release`** (잠금 해제) | ❌ **0회** | **잠금은 프로그램 종료 시에만 풀림 → 결함 2 악화** |

`journal/write`가 호출되지 않는다는 것은 특히 아픕니다. 이 기능의 목적은 *"작성 중이던 내용을 프로그램이 죽어도 복구"* 인데, **기록하는 쪽이 없어서 복구할 것이 영구히 없습니다.** 프로그램은 파일을 열 때마다 "미저장 변경이 있나?" 물어보고 항상 "없다"는 답만 받습니다. 위험 R-08("사용자가 내보내기 없이 페이지를 닫아 편집 내용이 유실됨 — 발생가능성 High, 영향 High")의 완화책이 **연결이 안 된 상태**입니다.

#### 🟠 결함 5. 모든 PC에 파이썬을 설치해야 합니다

`PM_APP.py`는 `.exe`가 아닙니다. 실행 조건:

- **Python 3.9 이상**이 각 사용자 PC에 설치되어 있어야 합니다 (코드가 명시적으로 확인 후 거부).
- **tkinter**(파일 선택 창)가 함께 설치되어 있어야 네이티브 대화상자가 뜹니다. 없으면 화면 내 파일 탐색기로 대체되는데, 이는 **미리 정직하게 확인해서 알려주도록** 되어 있습니다(좋은 설계). 실제 테스트 환경에서 `file dialogs in the page (no tkinter here)`로 표시되는 것을 확인했습니다.
- **`.py` 파일을 더블클릭하면 파이썬이 실행되도록** 파일 연결이 되어 있어야 합니다.

제약 많은 사내 PC에서는 이 3가지가 모두 관문이 됩니다. 일반적으로 회사 표준 PC에는 파이썬이 없습니다.

#### 🟠 결함 6. `os.access()`로 쓰기 권한을 판단하는 것은 **윈도우에서 신뢰할 수 없습니다**

```python
def writable(d):
    return os.access(d, os.W_OK)
```

`paths.py`의 이 함수가 "공유 폴더에 쓸 수 있는가"를 판정합니다. 문제는 **윈도우에서 `os.access`는 NTFS/SMB의 권한(ACL)을 제대로 보지 않고 "읽기 전용 속성" 정도만 본다**는 점입니다. 즉 **쓰기 권한이 없는 공유 폴더를 "쓸 수 있다"고 잘못 판정**할 수 있습니다.

이것이 아픈 이유는, 이 판정의 존재 목적이 바로 그것을 막는 것이었기 때문입니다. `launch.py` 주석: *"NR-DEP-09는 읽기 전용 폴더를 **실행 시점**에 알려야 한다고 말한다 — 첫 저장 때 알게 되는 것은 최악의 순간이다."* 좋은 원칙인데 **판정 수단이 윈도우에서 부정확해서 원칙이 지켜지지 않을 수 있습니다.**

#### 🟡 결함 7. 변경 이력(CSV)을 여러 명이 동시에 쓰면 섞일 수 있습니다

`audit_append`가 CSV 파일에 이어쓰기(append)합니다. 코드 주석은 *"한 번의 write() 호출로 짧은 줄을 이어쓰면 OS가 끼워넣지 않는다"* 고 주장합니다. **로컬 리눅스 디스크에서는 맞는 말입니다.** 하지만:

- 파이썬의 텍스트 파일은 **버퍼링**되어 여러 줄이 뭉쳐 나가거나 8KB에서 쪼개집니다.
- **윈도우 SMB 공유 폴더에서는 이어쓰기의 원자성이 보장되지 않습니다.**

여러 사람이 동시에 저장하면 **변경 이력 한 줄이 다른 줄 중간에 끼어들어 CSV가 깨질 수 있습니다.** 이력 자체가 목적인 파일에서는 무시할 수 없는 위험입니다. (제약 산업에서 감사 추적이 깨지면 그 자체가 지적 사항이 됩니다.)

## 3부. 다른 Claude(또는 다른 개발자)에게 넘길 때의 공백

"이 작업을 한 Claude와 **다른** Claude에게 전달하여 운영 환경에서 쓸 수 있는지" 가 질문의 일부였으므로, 인수인계 관점에서 별도로 점검했습니다.

### 3.1 가이드 문서가 약속한 것 vs zip에 실제로 있는 것

`PRAP_AI_Agent_Guide.md`는 "AI 에이전트를 위한 지침서"로서 **매우 잘 쓰여 있습니다.** 규칙 7개("사용자 워크북을 절대 덮어쓰지 마라", "파생 열을 쓰지 마라" 등), 데이터 모델 10개 시트 전체, 검증 규칙 36개, 작업 레시피 5개가 정리되어 있습니다. **다른 AI에게 넘기기 위한 문서로서는 모범적입니다.**

문제는 **가이드가 지시하는 도구가 zip에 없다**는 점입니다.

| 가이드가 쓰라고 지시하는 것 | zip에 있는가 |

### 3.2 이것이 실제로 의미하는 것

> **비유**: 정밀기계와 함께 **완벽한 정비 매뉴얼**을 받았습니다. 매뉴얼에는 "3번 게이지로 압력을 측정하고, 7번 렌치로 조정하라"고 적혀 있습니다. 그런데 **공구함이 함께 오지 않았습니다.**

새 담당자(사람이든 AI든)는 다음 상황에 놓입니다.

1. **데이터를 고칠 수는 있지만 고친 결과가 맞는지 확인할 수 없습니다.** → 검증 없이 납품하게 되고, 가이드가 가장 경계하는 *"오류가 있어도 화면에 숫자는 나오고, 그 숫자가 틀렸다는 걸 사용자는 못 본다"* 는 상황이 됩니다.
2. **파이썬 껍데기를 수정할 설계 근거가 없습니다.** 코드 주석은 훌륭하지만, `NR-DEP-09`, `Q-N16`, `S-N06` 같은 규칙 번호를 참조하는데 그 규칙이 적힌 문서가 없습니다.
3. **회귀 테스트가 없습니다.** 검증 스크립트 9개가 전부 없으므로, 무엇을 고쳐도 "다른 것을 깨뜨렸는지" 알 수 없습니다.

## 4부. 서버 구동을 위해 추가로 필요한 사항 (요청사항 a, b)

전제: **중앙 서버 + 데이터베이스로 재구축**하는 방향으로 설계했습니다.

### 4.1 왜 "고치기"가 아니라 "다시 만들기"인가

먼저 이것이 과한 결론이 아니라는 근거를 들겠습니다.

**① 요청하신 두 기능이 설계서에서 명시적으로 배제되어 있습니다.**

개발계획서 v2.54 `02_Scope` 시트 **Out of scope**:

> | 제외 항목 | 이유 | 상태 |
> |---|---|---|
> | Multi-user concurrent editing, or any server / database component. | Requirement is a local single-file HTML tool. | **Confirmed Q-12** |
> | Authentication, user accounts, permissions. | No server; the workbook carries whatever access control the file share provides. | **Confirmed Q-12** |

그리고 가정 **A-06**: *"Only one person maintains the workbook at a time - no concurrent editing to reconcile."* (상태: Standing = 현재도 유효)

즉 **요청사항 a)b)는 설계의 가장 근본 전제를 뒤집는 요구**입니다. 이것은 프로그램이 잘못 만들어졌다는 뜻이 아닙니다. **요구사항이 바뀌었다**는 뜻입니다.

**② 현재 구조로는 물리적으로 불가능한 지점이 있습니다.**

| 요청 | 현재 구조에서 불가능한 이유 |
|---|---|
| **관리자만 General assumptions 수정** | 서버가 **사용자 자신의 PC에서 사용자 권한으로 돌아갑니다.** 화면에서 버튼을 숨겨도 그 사람은 (a) 데이터 파일이 그냥 JSON 텍스트라 메모장으로 열어 고칠 수 있고, (b) `index.html`을 직접 수정할 수 있고, (c) 브라우저 개발자 도구로 제한을 풀 수 있습니다. **자기 집 문을 자기가 잠그는 자물쇠**입니다. |
| | 게다가 신원이 **사용자가 직접 타이핑한 이름**입니다 (`identity_set`). 검증이 전혀 없어 아무 이름이나 적을 수 있습니다. **"관리자"라고 타이핑하면 관리자가 됩니다.** |
| **레코드 단위 잠금** | 현재는 **계획 파일 전체를 브라우저 메모리에 올리고 전체를 한 파일로 저장**합니다. "PRJ-001만 잠근다"는 개념이 성립할 자리가 없습니다. 파일 안의 한 레코드만 바꿔 쓰는 기능도, 어떤 레코드가 편집 중인지 기록할 곳도 없습니다. |
| **여러 명 동시 편집** | 현재 잠금은 **파일 전체 배타 잠금**입니다. A가 편집 중이면 B·C·D는 **아무것도** 편집할 수 없습니다. 이는 "동시 편집"의 반대입니다. |

**③ 그러나 버릴 것은 거의 없습니다.**

이것이 핵심입니다. 재구축이라고 해서 처음부터 다시 만드는 것이 아닙니다.

| 자산 | 재사용 여부 | 비고 |
|---|---|---|
| **계산 엔진** (`index.html` 내 계산 로직) | ♻️ **그대로 재사용** | 가장 값비싼 자산. 36개 검증 규칙 + 기간 도출 + FTE 공식. 순수 함수로 분리되어 있다고 설계서가 보증(`07_Architecture` 레이어 5: *"화면도 파일도 건드리지 않는다"*). |
| **화면 전체** (탭, 표, 그래프) | ♻️ **거의 그대로** | 데이터를 파일이 아니라 서버 API에서 받도록 바꾸는 작업만. |
| **데이터 모델** (10개 시트, 열 정의) | ♻️ **그대로 → DB 테이블로 번역** | 이미 부모-자식 관계와 키가 정의되어 있어 DB 스키마로 기계적 번역이 가능합니다. |
| **검증 규칙 36개** | ♻️ **그대로** | 서버에서도 돌려야 함(아래 4.3 ⑤). |
| **원자적 저장 절차** (`workspace.py`) | 🔄 **DB 트랜잭션으로 대체** | 역할이 DB로 넘어갑니다. |
| **파일 잠금** (`claim.py`) | 🔄 **DB 잠금 테이블로 대체** | 설계 사상(30초/30분 분리, 실명 안내)은 **그대로 계승**. 훌륭한 설계입니다. |
| **로컬 HTTP 서버** (`server.py`) | 🔄 **실제 서버로 승격** | API 목록 28개가 이미 정의되어 있어 출발점이 됩니다. |
| **파일 선택 창** (`files.py`) | 🗑️ 불필요 | 서버 방식에서는 없어집니다. |

> **비유**: 훌륭한 **엔진과 계기판**을 가진 1인승 경비행기가 있습니다. 요청은 "여러 명이 타는 여객기"입니다. **동체(구조)는 새로 만들어야 하지만, 엔진과 계기판은 그대로 옮겨 달 수 있습니다.** 그리고 엔진이 전체 비용의 절반 이상입니다.

### 4.2 목표 구조

```
[ 사용자 A 브라우저 ]  ┐
[ 사용자 B 브라우저 ]  ├── HTTPS ──▶ [ 사내 서버 1대 ]
[ 사용자 C 브라우저 ]  ┘                ├ 웹 서버 (IIS 또는 nginx)
  └ 화면 + 계산 엔진                     ├ 애플리케이션 (Python / FastAPI)
    (index.html 재사용)                  │   ├ 인증·권한 확인
                                         │   ├ 레코드 잠금 관리   ← 요청 b)
                                         │   ├ 검증 규칙 재실행
                                         │   └ 변경 이력 기록
                                         ├ 데이터베이스 (PostgreSQL)
                                         │   ├ 업무 데이터 (10개 시트 → 테이블)
                                         │   ├ 잠금 테이블
                                         │   ├ 사용자·권한 테이블
                                         │   └ 변경 이력 테이블
                                         └ 사내 AD 연동 (로그인)
```

**이 구조로 바뀌면서 덤으로 해결되는 것들**:

- **프로그램 업데이트가 서버 1곳만 갱신**하면 됩니다. (지금은 전원이 각자 다시 받아야 함)
- **각 PC에 파이썬 설치가 불필요**해집니다 → 결함 5 해소.
- **작업 유실(결함 3)이 구조적으로 불가능**해집니다 → DB 트랜잭션이 보장.
- **변경 이력이 깨질 수 없습니다** → DB가 보장, 결함 7 해소.
- **모두가 항상 같은 숫자를 봅니다** (지금은 각자 자기 메모리의 데이터로 계산).

#### ② 데이터베이스 — **PostgreSQL 권장**

**왜 PostgreSQL인가** (장단점 평가 후 결론):

| 후보 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **PostgreSQL** | 무료. 행 단위 잠금(`SELECT … FOR UPDATE`)이 정석적으로 강력. 트랜잭션 신뢰도 최상급. 윈도우에서 잘 돌아감. 인력 구하기 쉬움 | 사내에 DBA가 없으면 초기 학습 필요 | ✅ **권장** |
| SQL Server | 사내가 MS 환경이면 관리 도구·AD 연동이 자연스러움 | **라이선스 비용**. 에디션에 따라 수백만 원~ | 🔸 사내에 **이미 SQL Server 운영 중이고 DBA가 있다면** 이쪽 |
| SQLite (파일형 DB) | 설치 불필요 | **네트워크 공유에서 동시 쓰기 취약** — 지금 문제를 반복함 | ❌ 부적합 |
| 지금처럼 파일 방식 유지 | 변경 최소 | 레코드 잠금·권한·트랜잭션 전부 직접 구현 = DB를 다시 만드는 일 | ❌ 부적합 |

> **결론: PostgreSQL.** 단, 사내에 SQL Server가 이미 운영 중이고 관리 인력이 있다면 SQL Server로 바꿔도 설계는 그대로 성립합니다.

**테이블 구조** — 기존 10개 시트가 거의 1:1로 번역됩니다.

```
project              ← Project 시트 (25열)
milestone            ← Milestone
project_period       ← ProjectPeriod
person               ← Person
assignment           ← Assignment
person_period_weight ← PersonPeriodWeight
monthly_estimate     ← MonthlyEstimate
-- 이하는 "General assumptions" = 관리자 전용 (요청 a)
period_fte_standard  ← PeriodFTEStandard
role_factor          ← RoleFactor
value_list           ← Lists
config               ← Config
-- 이하는 신규
app_user             사용자·권한
record_lock          레코드 잠금          ← 요청 b)
change_log           변경 이력 (기존 CSV 대체)
assumption_version   가정값 버전 관리
```

**모든 업무 테이블에 `row_version` 열을 추가**합니다 (수정할 때마다 1씩 증가). 저장 시 "내가 읽은 버전이 아직 그대로인가?"를 확인해서, 혹시 잠금이 빠져나가도 **결함 3(작업 유실)이 절대 일어나지 않게** 이중 안전장치를 겁니다.

#### ③ 애플리케이션 서버 — **Python + FastAPI 권장**

**왜 파이썬인가**: 기존 코드가 파이썬입니다. `storage/workspace.py`의 저장 규칙, `claim.py`의 잠금 판단 로직, `timefmt.py`의 시각 처리를 **그대로 옮겨올 수 있습니다.** 다른 언어를 고르면 이 자산을 버립니다.

**왜 FastAPI인가**: 이미 `server.py`에 28개 API가 정의되어 있고, FastAPI는 그 구조와 거의 같은 모양으로 쓸 수 있습니다. 자동 API 문서 생성은 인수인계 시 큰 이점입니다.

#### ④ 인증 — **사내 AD(도메인) 연동 권장**, 다만 확인 필요

인증 방식이 "아직 미정"이라고 하셨으므로 **두 안을 모두 제시하고, 사내 IT팀에 물어볼 질문**을 정리합니다.

| | **안 1: 사내 AD 연동 (권장)** | **안 2: 앱 자체 계정** |
|---|---|---|
| 로그인 방법 | 윈도우 로그인 그대로 (추가 입력 없음) | 앱 전용 ID/비밀번호 |
| 관리자 지정 | AD 그룹 `PRAP-Admins`에 넣기 | 앱 화면에서 체크 |
| 비밀번호 관리 | **불필요** (회사 정책이 자동 적용) | 초기화·만료·복잡도 정책을 직접 만들어야 함 |
| 퇴사자 처리 | **자동** (AD 계정 정지 시 즉시 차단) | 수동 (누락 위험) |
| 보안 감사 | 회사 표준에 포함 | 별도 설명 필요 |
| 구축 난이도 | 중 (IT팀 협조 필수) | 하 (혼자 가능) |
| 개발 기간 | +1~2주 | +3~5일 |

> **권장: 안 1 (AD 연동).** 이유는 보안이 아니라 **운영 부담**입니다. 안 2는 "비밀번호를 잊었다", "퇴사자 계정이 살아 있다" 같은 일을 **영구히 담당자가 처리**해야 합니다. 제약 산업에서는 접근 권한 관리 기록 자체가 감사 대상이 되므로, 회사가 이미 갖춘 체계에 얹는 것이 압도적으로 유리합니다.

**사내 IT팀에 물어볼 질문 8개** (그대로 전달하셔도 됩니다):

1. 사내 웹 애플리케이션에서 **Windows 통합 인증(Kerberos/NTLM) 또는 LDAP 조회**를 쓸 수 있습니까? 승인 절차는 무엇입니까?
2. 그 용도로 쓸 수 있는 **서비스 계정(service account)** 을 발급받을 수 있습니까?
3. 권한 구분용 **AD 보안 그룹을 신규 생성**할 수 있습니까? (예: `PRAP-Admins`, `PRAP-Editors`) 생성·구성원 변경은 누가 합니까?
4. 사내 전용 **가상 서버(VM) 1대**를 받을 수 있습니까? 사양·OS·백업 정책은 어떻게 됩니까?
5. 사내 **HTTPS 인증서**를 발급받을 수 있습니까? (`https://prap.사내도메인` 형태)
6. **PostgreSQL을 사내 서버에 설치**하는 데 제약이 있습니까? 이미 표준 DB(SQL Server 등)가 지정되어 있습니까?
7. 사내 웹 애플리케이션 도입 시 **거쳐야 하는 승인/검증 절차**(IT 변경관리, 보안 검토, CSV/밸리데이션)가 무엇입니까? 소요 기간은?
8. 이 도구는 임상시험 **자원 계획** 데이터만 다루고 환자 데이터·임상 원천데이터는 다루지 않습니다. 이 경우에도 **GxP 시스템 검증(CSV) 대상**입니까? (범위가 크게 달라지므로 반드시 사전 확인)

#### ⑤ 검증 규칙을 서버에서도 돌려야 합니다

지금은 검증 36개가 브라우저에서만 돕니다. 서버 방식에서는 **서버에서 반드시 다시 돌려야 합니다.** 이유는 브라우저를 믿을 수 없기 때문입니다 — 개발자 도구로 검증을 건너뛰고 데이터를 보낼 수 있습니다.

> **비유**: 은행 창구에서 고객이 미리 계산해온 금액을 그대로 믿지 않고, 창구에서 다시 셉니다. 고객을 의심해서가 아니라 **그게 창구의 일**이기 때문입니다.

권장 접근: **계산·검증 로직을 파이썬으로 한 번 옮기고, 그것을 정답으로 삼습니다.** (가이드가 언급한 `tools/prap_io.py`가 바로 이 일을 하는 파일입니다 — 그래서 3.3의 인수인계 항목 2번이 중요합니다. 그 파일이 있으면 이 작업의 상당 부분이 이미 끝나 있습니다.)

### 4.4 요청 b) — 레코드 단위 잠금 설계

주신 예시를 그대로 만족시키는 설계입니다.

#### 잠금 단위 두 가지

| 잠금 종류 | 대상 범위 | 언제 |
|---|---|---|
| **프로젝트 잠금** | `project` 행 + 그 프로젝트의 `milestone`, `project_period`, `monthly_estimate`, **그리고 그 프로젝트의 모든 `assignment`** | 프로젝트 기간·마일스톤·기간 가중치·월별 FTE를 수정할 때 |
| **배정 잠금** | `assignment` 한 행 + 그 배정의 `person_period_weight`, `monthly_estimate` | 배정 기간·인원 가중치·월별 가중치를 수정할 때 |

#### 왜 프로젝트 잠금이 배정까지 포함해야 하는가

이 부분이 설계의 핵심이고, 놓치면 숫자가 틀립니다.

> **비유**: 프로젝트 기간은 **건물의 층 구분선**이고, 배정은 **각 층에 들어가는 사무실**입니다. 누군가 층 구분선을 옮기면 **모든 사무실의 위치가 함께 바뀝니다.** 그래서 층 구분선을 만지는 동안에는 사무실을 아무도 옮길 수 없어야 합니다.

구체적으로: `PRJ-001`의 기간 경계를 바꾸면 → 각 월이 속한 기간이 바뀌고 → `period_weight`가 바뀌고 → **그 프로젝트 모든 배정의 월별 FTE가 재계산됩니다.** 그래서 프로젝트를 잠근 동안 하위 배정 편집을 허용하면 두 사람이 서로의 계산 근거를 흔들게 됩니다.

반대 방향도 막아야 합니다. B가 `ASG-007`을 편집 중인데 A가 `PRJ-001` 전체를 잡아버리면, B의 작업이 밑에서 무너집니다. 그래서 **배정을 잠글 때 부모 프로젝트에 "의도 표시(intent)"를 남깁니다.** 이 표시가 있으면 프로젝트 전체 잠금을 거부합니다.

> 이 방식은 데이터베이스 이론에서 **다중 단위 잠금(multi-granularity locking)** 이라 부르는 표준 기법입니다. 새로 발명한 것이 아니라 40년간 검증된 방식입니다.

#### 동작 표 — 주신 예시를 포함해서

| # | 요청 | 현재 걸린 잠금 | 결과 | 사용자에게 보이는 메시지 |
|---|---|---|---|---|
| 1 | A가 `PRJ-001` 기간 수정 | 없음 | ✅ 허용 | "PRJ-001을 편집 중입니다" |
| 2 | **B가 `PRJ-001` 기간 또는 월 FTE 수정** | **A가 PRJ-001 잠금** | ❌ **차단** | **"김OO(DM팀)이 PRJ-001을 편집 중입니다. 11:31 시작, 현재 활동 중."** ← 요청 예시 1 |
| 3 | B가 `PRJ-001`의 `ASG-007` 수정 | A가 PRJ-001 잠금 | ❌ 차단 | "김OO이 PRJ-001 전체를 편집 중이라 이 배정도 수정할 수 없습니다" |
| 4 | B가 `PRJ-001`의 `ASG-007` 수정 | 없음 | ✅ 허용 | "ASG-007을 편집 중입니다" (PRJ-001에 의도 표시) |
| 5 | **C가 같은 `ASG-007` 수정** | **B가 ASG-007 잠금** | ❌ **차단** | **"이OO(DM팀)이 이 배정을 편집 중입니다"** ← 요청 예시 2 |
| 6 | C가 `PRJ-001`의 **다른** `ASG-009` 수정 | B가 ASG-007 잠금 | ✅ **허용** | — (**진짜 동시 편집이 되는 지점**) |
| 7 | A가 `PRJ-001` 전체 수정 | B가 ASG-007 편집 중 | ❌ 차단 | "이OO이 이 프로젝트의 배정(ASG-007)을 편집 중입니다" |
| 8 | D가 `PRJ-002` 수정 | 위 전부 | ✅ 허용 | — (다른 프로젝트는 완전 독립) |

**6번 줄이 이 설계의 성과입니다.** 지금은 A가 편집하면 B·C·D가 전부 막히는데, 이 설계에서는 **같은 프로젝트 안의 서로 다른 배정을 여러 명이 동시에 편집할 수 있습니다.**

#### 잠금 테이블

```
record_lock
  lock_id        잠금 번호
  scope          'project' | 'assignment' | 'assumptions'
  record_id      'PRJ-001' 또는 'ASG-007'
  mode           'exclusive'(전용) | 'intent'(의도 표시)
  parent_id      배정 잠금일 때 부모 프로젝트 ID
  user_id        누가
  user_name      실명 (메시지에 표시)
  department     부서 (메시지에 표시)
  acquired_at    획득 시각
  heartbeat_at   마지막 생존 신호          ← 기존 claim.py 사상 계승
  expires_at     만료 시각
  UNIQUE (scope, record_id, mode)          ← DB가 중복을 원천 차단
```

`UNIQUE` 제약이 핵심입니다. 두 사람이 **완전히 동시에** 같은 레코드를 요청해도 **DB가 한 명만 통과시킵니다.** 프로그램이 판단하지 않고 DB가 판단하므로 틀릴 여지가 없습니다. (기존 `claim.py`가 `O_EXCL`로 노린 것과 **똑같은 원리**를, 훨씬 강력한 수단으로 구현하는 것입니다.)

#### 잠금 획득·유지·해제 규칙 — 기존 설계 사상 계승

기존 `claim.py`의 좋은 판단들을 그대로 가져옵니다.

| 규칙 | 값 | 기존 코드에서 계승한 이유 |
|---|---|---|
| 잠금 시점 | **값이 실제로 바뀔 때** (열 때가 아님) | *"계획을 잠깐 보다 점심 간 사람이 팀을 30분 막는다"* |
| 생존 신호 | **30초**마다 | "이 사람 살아있나" |
| 만료 | **30분** | "남이 가져가도 되나" — 두 값을 분리 |
| 자기 세션 복구 | **즉시** | *"남의 계획에서 30분 막히는 건 정책이고, **내 계획**에서 30분 막히는 건 방해다"* |
| 해제 시점 | 저장 후 **명시적 완료** 시 + 로그아웃 시 + **다른 레코드로 이동할 때** | ← **결함 2를 여기서 근본 해결** |
| 차단 메시지 | **실명 + 부서 + 시작 시각 + 해제 예정 시각** | *"파일이 사용 중입니다"는 행동으로 옮길 수 없다* |

**결함 2(잠금 미해제)를 반복하지 않기 위한 3중 안전장치**:

1. 다른 레코드로 이동하면 **이전 잠금을 반드시 해제** (기존 결함의 직접 수정)
2. 30분 자동 만료 (DB의 `expires_at` 기준, 주기적 정리)
3. **관리자 화면에 "현재 잠금 목록"** 을 두고 강제 해제 버튼 제공 — 지금은 이런 수단이 아예 없습니다

#### ⚠️ 놓치기 쉬운 문제 하나: "사람" 축의 충돌

설계상 반드시 짚어야 할 지점입니다.

한 사람(`PSN-005`)이 프로젝트 3개에 배정되어 있다고 하겠습니다.

```
B가 PRJ-001의 PSN-005 배정을 0.4 → 0.6으로 올림   (잠금: ASG-007)
C가 PRJ-002의 PSN-005 배정을 0.3 → 0.5로 올림     (잠금: ASG-021)
```

**두 사람 다 정당하게 허용됩니다** (서로 다른 배정이므로). 그런데 결과는 `PSN-005`의 월 합계가 **1.1 FTE**가 되어 과다배정 경고선(1.5)에 접근합니다. **B도 C도 자기 화면에서는 그 사실을 볼 수 없습니다.**

> **비유**: 두 부서장이 각자 같은 직원의 일정을 잡았습니다. 각자 자기 몫은 합리적인데, **합치면 그 사람은 주 60시간을 일해야 합니다.** 둘 다 잘못한 게 없는데 결과는 잘못되었습니다.

이것은 잠금으로 풀 문제가 아닙니다(잠가버리면 동시 편집을 포기하는 것). **알려주기로 풀어야 합니다.**

권장 처리:
- 배정 저장 시 서버가 **해당 인원의 전체 월별 합계를 재계산**하고, 과다/과소 배정이 새로 발생하면 **즉시 화면에 경고**를 띄웁니다 (막지는 않음).
- 같은 인원의 다른 배정을 누군가 편집 중이면 **"이OO이 홍길동의 다른 배정(PRJ-002)을 편집 중입니다 — 합계가 바뀔 수 있습니다"** 라고 **정보성 안내**를 띄웁니다.
- 인원별 과다배정 목록을 **대시보드에 상시 노출**합니다.

### 4.5 요청 a) — 관리자 권한 분리 설계

#### 권한 3단계

| 권한 | 할 수 있는 일 | 대상 |
|---|---|---|
| **관리자 (Admin)** | 전부 + **General assumptions 수정** + 사용자·권한 관리 + 잠금 강제 해제 + 이력 조회 | 1~2명 |
| **편집자 (Editor)** | 프로젝트·인원·배정 데이터 편집. **General assumptions는 읽기만** | 실무 담당자 |
| **조회자 (Viewer)** | 전부 읽기만. 엑셀 내보내기 가능 | 팀장·유관부서 |

#### "General assumptions"가 정확히 무엇인가

코드에서 확인했습니다. `index.html`의 General assumptions 탭은 **4개 테이블**을 담당합니다.

```javascript
PeriodFTEStandard:"General assumptions", RoleFactor:"General assumptions",
Lists:"General assumptions",            Config:"General assumptions",
```

| 테이블 | 내용 | 바꾸면 어떻게 되는가 |
|---|---|---|
| `PeriodFTEStandard` | 프로젝트 유형·상별 표준 월 FTE (88행) | **모든 임상시험 프로젝트의 숫자가 바뀜** |
| `RoleFactor` | 역할별 업무 비중 (430행) | **모든 배정의 숫자가 바뀜** |
| `Lists` | 허용 값 목록 (역할명, 기간명, 시스템명 등) | 데이터 입력 가능 범위가 바뀜 |
| `Config` | 설정값 (과다배정 기준 1.5, FTE 시간 160 등) | **모든 경고 판정 기준이 바뀜** |

> **비유**: 이 4개는 **환율표**입니다. 개별 프로젝트 데이터가 "금액"이라면, 이것은 그 금액을 원화로 환산하는 환율입니다. **환율을 한 칸 바꾸면 회사 모든 장부의 숫자가 동시에 바뀝니다.** 관리자만 만지게 하려는 판단은 정확합니다.

#### 가정값 변경은 "잠금"이 아니라 "버전"으로 다루는 것을 권장합니다

가정값을 잠금으로만 다루면 이런 일이 생깁니다.

```
14:00  B가 PRJ-001을 편집 중 (화면에 표시된 FTE는 role_factor 0.90 기준)
14:05  관리자가 role_factor를 0.90 → 1.10으로 변경
14:10  B가 저장 → B의 화면 숫자와 DB의 실제 계산값이 다름
```

**권장 방식**:

1. 관리자가 가정값을 수정하면 **새 버전으로 저장**합니다 (`assumption_version` 테이블, 적용 시작일 포함). **덮어쓰지 않습니다.**
2. 저장 시 관리자에게 **영향 범위를 먼저 보여줍니다** — "이 변경으로 프로젝트 62개, 인원 20명의 월별 FTE가 바뀝니다. 새로 과다배정되는 인원 3명: …" → 확인 후 적용.
3. 적용되면 편집 중인 사용자들에게 **"기준값이 변경되었습니다. 화면을 새로 고쳐야 합니다"** 라고 알립니다.
4. 과거 버전이 보존되므로 **"지난달 보고서의 숫자는 어느 기준이었나"** 에 답할 수 있습니다. (제약 산업 감사 대응에 중요)

이 방식은 기존 설계의 철학과도 맞습니다 — 개발계획서가 은퇴한 검증 규칙(V-25, V-28)까지 기록으로 남긴 것과 같은 사고방식입니다.

#### 반드시 지켜야 할 원칙: **권한 확인은 서버에서**

> **비유**: 화면에서 버튼을 숨기는 것은 **금고 앞에 "직원 외 출입금지" 안내판을 세우는 것**입니다. 서버에서 확인하는 것은 **금고에 자물쇠를 다는 것**입니다. 안내판만으로는 아무것도 막지 못합니다.

구체적으로:

- 버튼 숨김·회색 처리는 **친절함**이지 보안이 아닙니다. (그래도 해야 합니다 — 사용자가 헛수고하지 않도록)
- `PeriodFTEStandard`, `RoleFactor`, `Lists`, `Config`를 수정하는 **모든 API가 요청자 권한을 확인**하고, 관리자가 아니면 거부합니다.
- 거부 기록을 **변경 이력에 남깁니다** (누가 무엇을 시도했는지).
- **DB 직접 접근 권한을 일반 사용자에게 주지 않습니다.** 애플리케이션 전용 계정으로만 DB에 접근합니다. (지금은 데이터가 그냥 공유 폴더의 JSON 파일이라 누구나 메모장으로 고칠 수 있습니다.)
