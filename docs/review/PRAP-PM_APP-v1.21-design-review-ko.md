### 1.2 새 기능 — 배정 없는 프로젝트가 필요량을 말합니다

변경 내역의 설명을 옮기면 이렇습니다.

> *"프로젝트를 추가하고 기간을 정해도, 첫 사람을 배정하기 전까지 그 프로젝트는 **목록에는 있으나 비어 있습니다.** 모든 월이 빈칸입니다. **빈칸의 행은 비용이 들지 않는 프로젝트처럼 보이지, 아직 아무도 배정하지 않은 프로젝트처럼 보이지 않습니다** — 누구를 붙일지 결정할 때 봐야 하는 것과 정반대입니다."*

> **비유**: 식당 예약표에 "3번 테이블 — 6인 예약"이라고 적혀야 하는데 **빈칸**으로 남아 있었습니다. 빈칸은 "예약 없음"처럼 보이지만 실제로는 "예약은 있고 담당 서버만 안 정했음"이었습니다. 이제 **"6인 필요"** 라고 적어줍니다.

**실제로 작동하는지 확인했습니다.** 더미 데이터에서 한 프로젝트의 배정을 모두 지워보니, 변경 내역이 약속한 그대로 나타났습니다.

```
◦ 13.34 unstaffed
```

고리 표시(`◦`)와 함께 **별도 줄에** 합계가 붙습니다.

**그리고 가장 중요한 주장을 검증했습니다** — *"어떤 합계에도 더해지지 않아 프로젝트 표와 인원 표가 전과 똑같이 일치한다"*.

```
tools/test_app.py  (v1.51 엔진 × Dummy v1.18)
  ok   calculation matches the reference on all 1227 person-months
  ok   V-34 agrees with the reference on all 72 project-month(s) off their standard
  ok   export re-imports with no findings above information
FAILURES: none
```

**기존 참조 구현(`prap_io` v1.0)과 1,227건 전부 일치**했습니다. 즉 *"이미 가진 어떤 수치도 움직이지 않는다"* 는 주장이 사실입니다. 표시만 바뀌고 계산은 건드리지 않았습니다. **버전을 올리면서 숫자가 조용히 달라지는 것이 이 프로젝트에서 가장 위험한 사고인데, 그것이 일어나지 않았음을 확인했습니다.**

### 1.3 새 검증 규칙 V-36 — 문서와 코드가 일치합니다

스펙 v1.31에 이렇게 정의되어 있습니다.

> **V-36** | Information | *"기간은 있으나 배정 행이 전혀 없는 프로젝트. 계산에서 발생, 프로젝트당 하나. **INCOMPLETE로 분류되어 거부하지도 묻지도 않는다.**"*

변경 내역의 *"그것은 안내일 뿐 그 이상이 아니다. 편집을 거부하지 않고, 저장을 막지 않고, 질문하지 않는다"* 와 정확히 같습니다. **스펙과 코드가 어긋나지 않았습니다.**

### 1.4 부수적으로 좋아진 것 — 검증 심각도에 등급이 생겼습니다

검증기 출력에 이전에 없던 표기가 보입니다.

```
error       [must]        V-19  ...
error       [conditional] V-23  ...
1 of them are [must]: the application refuses those rows until they are corrected.
The rest it reports, and asks about at Save.
```

**"오류"를 한 덩어리로 묶지 않고 "거부하는 것"과 "보고하고 저장 때 묻는 것"으로 갈랐습니다.** 사용자가 무엇을 지금 고쳐야 하는지 알 수 있게 되었으므로 실질적인 개선입니다.

### 2.3 왜 v1.21의 테스트는 통과하는가 — 이것이 핵심입니다

배포된 v1.21을 자체 종단간 테스트에 넣으면 **0 failed**로 통과합니다.

```

  ok   taking the claim writes a marker beside the plan
  ok   which names the person a blocked colleague should ask
  ok   and the page can see that it holds it
...
0 failed
```

**테스트 스위트가 세 공백을 검사하지 않기 때문에 통과합니다.** 잠금을 *잡는* 것은 검사하지만 *놓는* 것은 검사하지 않고, 정전 감지와 복구 기록은 검사 항목 자체가 없습니다.

> **비유**: 자동차 검사에서 **브레이크를 밟으면 멈추는지**는 보지만 **주차 브레이크를 풀면 풀리는지**는 보지 않습니다. 그래서 주차 브레이크가 안 풀리는 차가 매번 검사를 통과합니다. 검사표에 그 항목이 없기 때문입니다.

**이것이 3판에서 12번 항목(배선 테스트 추가)을 권고한 이유이고, v1.21이 나온 뒤에도 그 권고가 유효한 이유입니다.**

## 3. 새로 발견한 문제

### 🔴 새 결함 I. 함께 온 템플릿이 7세대 뒤처진 구버전입니다

```
PRAP_SourceData_Template_v1.6.xlsx      시트 11개   schema_version = 5
PRAP_SourceData_Dummy_10x10_v1.9.xlsx   시트 12개   schema_version = 11
현재 애플리케이션이 기대하는 값                      schema_version = 12
```

이전 업로드에 있던 것은 `Template_v1.16`(schema 12)였습니다. **이번에 온 것은 `v1.16`이 아니라 `v1.6`입니다** — 한 글자 차이지만 7세대 전 파일입니다.

**추측이 아니라 검사해봤습니다.**

```
python3 tools/prap_io.py validate PRAP_SourceData_Template_v1.6.xlsx

  error  [must]        V-19  PeriodFTEStandard  PRJ-001: no standard weight for
                             NewDrug CT / Phase 1 / any scope / Start-up.
  error  [conditional] V-23  RoleFactor         No role factor for ... Lead data
                             manager — 4 person-month(s) were calculated at
                             factor 1.00 instead.
  warning              V-09  Config             This file is schema version 5;
                             this build expects 12.

4 finding(s): 2 error, 1 warning, 1 information
1 of them are [must]: the application refuses those rows until they are corrected.
```

**두 가지가 나쁩니다.**

**① `[must]` 오류** — 애플리케이션이 해당 행을 **거부**합니다. 템플릿을 받아 작업을 시작하려는 사람이 첫 단계에서 막힙니다.

**② V-23이 더 위험합니다** — *"4 person-month가 factor 1.00으로 계산되었습니다."* AI Agent Guide가 이 규칙에 대해 직접 경고합니다 — *"빠진 factor는 V-23 오류다. 그렇지 않으면 계산이 조용히 1.00을 쓰게 된다."*

> **비유**: 환율표가 빠진 회계 장부를 받았는데, 프로그램이 멈추지 않고 **환율을 1:1로 가정해서** 계산을 계속합니다. 숫자는 나오고, 틀렸다는 표시는 경고 목록 안에 묻힙니다.

**조치는 간단합니다** — `Template_v1.16`(schema 12)으로 교체하면 됩니다. 이전 업로드에 있던 파일입니다.

> ### ✅ 결함 I 종결 — 그리고 뿌리까지 찾았습니다
>
> **v1.16을 받아 확인했습니다.** schema 12, 시트 12개, 검증 결과 **`0 findings — the file is clean`** 입니다. v1.6이 냈던 오류 2건이 전부 없습니다. 그리고 그 파일은 **두 브랜치의 `templates/` 안에 이미 들어 있던 것과 바이트 단위로 동일**했습니다(`80be8636…`). 즉 **저장소는 처음부터 올바른 파일을 갖고 있었고, 배포본에만 v1.6이 들어갔습니다.**
>
> 왜 그랬는지 찾았습니다. **문서 생성기가 "배포되는 빈 워크북은 v1.6"이라고 적고 있었습니다.**
>
> | 위치 | 문장 |
> |---|---|
> | `build_prog_spec.py:149` | *"데이터 스키마는 산문으로 기술하지 않는다. 이미 동작하는 파일로 존재한다 — `Template_v1.6.xlsx`, 그리고 sheet 03이 그 파일에 대한 parse contract를 문서화한다"* |
> | `build_prog_spec.py:649` | *"`Template_v1.6.xlsx` — 배포된 그대로의 빈 소스 워크북"* |
> | `build_prog_spec.py:678` | sheet 03 제목: *"Documents `Template_v1.6.xlsx`"* |
> | `build_dev_plan.py:2822` | 인도물 4.8: *"`PRAP_SourceData_Template_v1.6.xlsx` — Complete"* |
>
> 이것은 낡은 주석이 아니라 **무엇이 배포되는지를 정의하는 문서 본문**입니다. 그리고 판단이 아니라 사실이 틀렸습니다.
>
> | | 데이터 시트 | 컬럼 | schema |
> |---|---|---|---|
> | Template **v1.6** | 10개 | 81개 | **5** |
> | Template **v1.16** | 11개 | 92개 | **12** |
> | 사양서 `03_Data_Schema`가 실제로 문서화하는 것 | **11개** | 92개 | — |
>
> 사양서 sheet 03은 **v1.6에 존재하지 않는 시트 두 개**(`MonthlyEstimate`, `PeriodFTEStandard`)를 문서화하고, v1.6에만 있는 `PeriodWeightStandard`는 다루지 않습니다. 그러면서 표지에서는 v1.6을 문서화한다고 말하고 있었습니다.
>
> **네 곳을 정정하고 문서를 다시 생성했습니다**(번호는 유지 — 파일명 오류 정정이지 내용 추가가 아니므로). 바뀐 셀은 사양서 3개·계획서 1개로, 의도한 것뿐입니다. 저장소의 드리프트 검사기(`check_consistency.py`)가 매니페스트 해시 불일치를 잡아냈고, 지정된 해결책(`build_ai_reference.py`)으로 재생성해 **`PROBLEMS: none`** 으로 돌아왔습니다.
>
> **다만 검사기 자체에 빈틈이 하나 드러났습니다.** 이 드리프트를 잡기 위해 만들어진 검사기인데도 정정 전에 `PROBLEMS: none`이었습니다. **내용**은 v1.16과 정확히 대조하지만 **문서가 스스로 대는 파일명**은 검사하지 않습니다. 같은 종류의 어긋남이 다시 생길 수 있다는 뜻이므로, 검사 항목 추가를 권고합니다.

### ✅ D-10 종결 — 틀린 공식은 기계가 읽는 계약 파일에 있었습니다

3판에서 *"가이드 §5.1의 공식이 구현과 다르다"*고 지적했는데, 이번에 뿌리를 찾았습니다. **프로그래밍 사양서는 이미 올바르게 적고 있었습니다** — sheet 05가 R-32 개정 이후 세 줄 의사코드를 그대로 담고 있습니다. 틀린 것은 `tools/prap_contract.py` 한 곳이었고, 그것이 **`docs/prap_contract.json`(기계가 읽는 계약)** 과 **AI Agent Guide §5.1**로 흘러가고 있었습니다.

**얼마나 틀렸는지 수치로 재 봤습니다.** 동봉된 10x10 더미에서 배정이 1건뿐인 프로젝트-월을 골랐습니다.

```
PRJ-008  2029-03   (그 달에 배정 1건)
  standard_fte 1.67 × period_weight 1.07 × month_run 0.0333  =  demand 0.06 FTE
  애플리케이션이 내놓는 값                                      0.06 FTE
  문서의 공식(네 인자 곱)이 내놓는 값                            0.005 FTE   ← 12배 차이
```

고친 내용은 사양서의 세 줄을 계약 파일로 옮긴 것입니다.

```
demand(project, month)   = standard_fte( project, month ) x period_weight x month_run
claim(assignment, month) = ( role_factor / sharers ) x person_weight x coverage
fte(assignment, month)   = demand x claim / SUM( claims on that project-month )
```

**같은 공식을 쓰던 곳이 세 군데 더 있었습니다.** ① "빈 시작" 설명의 *"load는 person_weight × month_coverage로 축약된다"* — 실측하면 `0.39`가 아니라 **`0.96`**(= period_weight × month_run)입니다. ② 에이전트 작업 지시문의 같은 문장. ③ 가이드 §5.2의 예제 계산 자체(`1.20 × 0.90 × 0.40 × 0.7097 = 0.3066 FTE`).

**§5.2 예제는 동봉 더미로 누구나 재현할 수 있는 실측 예제로 바꿨습니다** — `PRJ-009` 2027-02, 세 사람이 있고 그중 둘이 같은 역할을 나눠 갖는 달입니다. 역할 인자 0.42를 두 사람이 **나누고**(각자 0.42가 아니라), 세 사람의 합이 프로젝트-월 1.29와 **센트까지 정확히** 일치하며, 마지막 1센트가 최대 잉여법으로 배분되어 `PSN-006`이 0.1443의 단순 반올림인 0.14가 아니라 **0.15**를 받는 것까지 보여줍니다. 손으로 검산했고, `prap_io.py calculate`로 자동 검산도 통과합니다.

### ✅ 파이썬이 없는 PC도 쓸 수 있게 — 설치하지 않고

사내 PC에 파이썬이 **있는** 것은 확인되었지만, **없는 PC도 있다**는 점이 남았습니다. 개발 계획서가 이미 이것을 route B의 갈림길로 적어 두었습니다 — *"노트북에 파이썬이 설치되어 있는가? 없다면 route B는 IT의 설치가 필요하다."*

**필요 없습니다.** Windows가 **embeddable package**를 배포합니다 — `python.exe`와 DLL, 표준 라이브러리를 담은 zip으로, **설치가 아니라 압축을 푸는 것**입니다. 레지스트리를 건드리지 않고, 관리자 권한이 필요 없고, PATH를 바꾸지 않고, 이미 있는 파이썬을 방해하지 않으며, 폴더를 지우면 사라집니다.

**이것이 되는 이유 세 가지를 모두 확인했습니다.**

| | 확인 방법 |
|---|---|
| 표준 라이브러리만 씀 → pip 없어도 무관 | 19개 모듈을 세었고, `test_layers.py`가 계속 강제하고 있었습니다 |
| **embeddable에는 tkinter가 없음** | 보통 이 아이디어가 죽는 지점입니다. **tkinter를 실제로 없애고 돌렸습니다** — 저장·재열기·폴더 탐색·편집 잠금 모두 정상이고, 앱이 스스로 *"file dialogs in the page (no tkinter here)"* 라고 알립니다 |
| `._pth` 가 `sys.path`를 고정하고 `PYTHONPATH`를 무시함 | `PM_APP.py`가 이미 자기 폴더를 `sys.path`에 넣고 있습니다. 그 줄이 사라지면 `bundle_runtime.py`가 **번들을 거부**합니다 — 멀리서 무게를 받치는 줄이고, 정리 한 번에 사라질 수 있는 종류입니다 |

**만든 것 세 개**

```
PM_APP.cmd              빌드가 앱 폴더에 넣습니다. runtime\python.exe 를 먼저 보고,
                        없으면 py -3, 그다음 python. 모든 경로는 %~dp0 기준,
                        CRLF·BOM 없음. 파이썬이 없을 때도, 앱이 시작에 실패할 때도
                        창이 닫히지 않고 멈춥니다 — 그 창에 설명이 있기 때문입니다
tools/bundle_runtime.py embeddable zip 을 앱 폴더에 풉니다. 사람들이 대신 집는
                        것(전체 배포판·설치 프로그램)을 각각 이름을 대며 거부합니다.
                        윈도우에서는 결과를 설명하지 않고 넣은 파이썬에게 직접 물어
                        확인합니다 — 다만 앱을 실행하지는 않습니다(아래 ✅ 항목)
check_pc.py             "이 PC가 돌릴 수 있는가"를 화면 12줄로. 앱 폴더 안에 함께
                        실립니다 — 물어봐야 할 사람이 바로 앱 폴더만 가진 사람이므로
```

**런처에서 진짜 위험을 하나 잡았습니다.** 파이썬 존재 여부를 알아보려고 `python`을 **실행하면 안 됩니다.** 윈도우 10·11은 `python.exe`에 대한 *app execution alias*를 기본으로 두고 있고, 그것을 실행하면 **Microsoft Store가 열립니다** — 파이썬이 없는 PC에서, 즉 이 런처가 존재하는 바로 그 PC에서. `where`는 **보기만 하므로**, 별칭을 찾아내 `WindowsApps` 경로로 알아보고 건너뜁니다. 시험이 아니라 **출시 전에 적대적으로 다시 읽다가** 발견했습니다.

**두 도구 사이의 함정도 막았습니다.** 다시 빌드하면 앱 폴더가 비워지고 런타임도 함께 사라집니다. 조용히 사라지는 것이 최악입니다 — 빌드한 기계에서는 그 기계의 파이썬으로 계속 동작하고, **파이썬이 없는 사람에게만** *"런타임이 제공되지 않았다"*고 말하게 됩니다. 이제 빌드가 그 사실을 말합니다. 그 시험은 처음에 **공허했고**(빌드 뒤에 런타임을 찾으니 늘 없음) 조건을 실제로 만들어 검사하도록 고쳤습니다.

```
test_no_python     FAILURES: none   (신규, 세 조각에 대한 검사)
전체 41개 스위트   41 통과 · 0 실패
```


### ✅ 결함 E 종결 — 팀 폴더는 있었고, 화면이 말하지 않았습니다

폴더는 실행할 때마다 만들어지고 있었고, 그 안에 용도를 적은 안내문도 들어 있었고, 서버는 그 경로를 화면에 넘겨주면서 주석에 *"화면이 이것을 열기·저장 위치로 제시한다"*고 적어 두었습니다. **화면은 그 값을 한 번도 읽지 않았습니다** — `where.shared` 언급 0회, 파일 창은 항상 개인 폴더에서 시작, 안내문을 가리키는 화면 0곳.

그래서 모든 계획서가 **자기만 열 수 있는 폴더**로 갔고, 거기서는 편집 잠금·"누가 편집 중"·덮어쓰기 방지·잠금 해제 알림이 **전부 죽은 코드**가 됩니다. 실패하지도, 경고하지도 않습니다 — 사람들이 그냥 메일로 복사본을 주고받게 됩니다.

**① 파일 창에 두 곳을 한 번 클릭으로.** `My plans` / `Team plans`, 현재 위치는 강조, 각각 무슨 뜻인지 한 줄씩. 기본 동작은 바꾸지 않았습니다 — 옳은 선택을 **쉽게** 만들었을 뿐 **몰래** 바꾸지 않았습니다.

**② 문제가 되는 순간에만 한 줄.** 조건을 *"개인 폴더에 있음"* 으로 하지 않았습니다. 개인 계획서 대부분은 일부러 개인 것이고, 매번 뜨는 막대는 일주일이면 가구가 됩니다. 조건은 **"개인 폴더에 있고 + 남이 저장했음"** 입니다 — 내 폴더에 있는데 남이 저장한 계획서는 **손으로 복사해 온 것일 수밖에 없고**, 그것이 이 결함이 일으키는 바로 그 실패입니다.

**옮기기는 네 개의 파일을 옮깁니다.** 계획서 하나는 `.prap` · `.journal`(저장 안 된 편집) · `.lock` · `backups\`의 이전 판본들입니다. 이름만 바꾸면 첫 번째만 옮기고 나머지를 버리며, 사람은 **보관된다고 들었던 이전 판본을 찾을 때** 그 사실을 알게 됩니다. **복사 → 읽어서 검증 → 그다음 삭제**로 만들었고, 중간에 실패하면 목적지에 만든 것을 도로 지우고 **원본은 손대지 않습니다.** 잠금은 경로가 바뀌므로 옮기지 않고 먼저 반납합니다 — 그 반납이 기다리던 사람에게 알림이 가는 경로이기도 합니다.

두 인스턴스로 전 과정을 재현했습니다.

```
이서연이 만든 계획서를 김민준이 자기 폴더로 복사해 온 상황
  화면 판정        private=True   target=<공유>/shared/workspaces/team.prap
  '팀 폴더로 옮기기' → 개인 폴더: 비어 있음 / 팀 폴더: ['team.prap']

  이서연이 열 수 있는가      예 — 프로젝트 1건
  이서연이 잠금을 잡음       True
  김민준이 편집하려 하면     차단됨 — "이서연 (DM) is editing this plan.
                                      Started 09:29, active now."
```

**마지막 줄이 이 결함의 해소입니다** — 잠금이 처음으로 실제로 무언가를 보호합니다.

#### 작업 중 가드가 저를 잡은 일

`test_layers.py`의 NR-DEP-05 검사가 실패했는데, 원인이 제 **문서화 문자열**이었습니다. 한 줄이 `from the source; ...` 로 시작해서 가드가 그것을 `import the` 로 읽었습니다. 그런데 그 파일에는 **바로 그 문제를 위해 쓴 `code_only()` 헬퍼**가 아래에 있었고 이 검사만 쓰지 않고 있었습니다. 헬퍼의 주석이 제 상황을 그대로 설명합니다 — *"주석이 실패시킬 수 있는 검사는, 사람들이 신뢰하는 대신 피해 가며 쓰게 되는 검사다."*

문장을 다르게 쓰면 증상은 사라지지만 **함정은 다음 사람에게 남습니다.** 그래서 가드가 코드를 읽도록 고쳤고, **약화되지 않았음을 증명했습니다** — 진짜 `import requests` 를 넣어 보면 그대로 잡고 파일명까지 댑니다.

```

test_python_app    0 failed               (알림·파일창 검사 9건 추가)
test_layers        FAILURES: none
전체 40개 스위트   40 통과 · 0 실패
```


### ✅ 결함 F 종결, 그리고 윈도우 실측을 **대부분 없앴습니다**

**결함 F**(사내 PC의 파이썬 설치)는 **가능함을 확인**하셨습니다(2026-09-14). 배포 관문이 사라졌습니다.

**윈도우 실측(R-N06)** 은 제약이 하나 드러나면서 접근을 바꿨습니다 — 사내에서 시험은 가능하지만 **결과 파일을 외부로 가지고 나올 수 없습니다.** 그래서 "어떻게 가지고 나올까"가 아니라 **"가지고 나올 것을 만들지 않으려면 어떻게 해야 하는가"** 로 문제를 바꿨습니다. 재려던 네 항목을 다시 보니 셋은 이미 잴 필요가 없거나 없앨 수 있었습니다.

| 재려던 것 | 어떻게 되었나 |
|---|---|
| SMB 수정시각 2초 반올림 | **측정 불필요.** 판단하던 두 곳을 모두 `last_saved` 토큰으로 바꾼 상태입니다. 남은 `st_mtime`은 백업 목록의 표시 시각뿐이고 아무 결정도 내리지 않습니다 |
| `os.access()` 권한 판정 | **설계로 제거.** OS에게 묻는 대신 **탐침 파일을 실제로 만들어 보고 지웁니다** |
| 이어쓰기 원자성 (결함 G) | **완화 유지.** 사람·월별 파일 분리 + flush |
| 정전 후 저널 복구 | 로직이 플랫폼 무관. 확인하고 싶다면 아래 스크립트가 답합니다 |

#### `os.access()` 를 왜 버렸는가

이것이 이번 변경의 핵심입니다. **윈도우에서 `os.access(d, os.W_OK)`는 ACL이 아니라 읽기 전용 속성만 봅니다**(파이썬의 알려진 동작이며 제가 측정한 것이 아닙니다). 그런데 공유 폴더 권한은 대개 ACL로 걸립니다. 그래서 **쓸 수 없는 폴더를 쓸 수 있다고 답할 수 있었고**, 그것은 NR-DEP-09가 존재하는 바로 그 경우입니다 — *"읽기 전용이면 첫 저장에서 실패하지 말고 launch 때 물어본다"*. 물어봐야 할 때 묻지 않고, **일을 다 한 뒤 저장할 때** 실패를 알리게 됩니다.

탐침 파일은 그런 식으로 틀릴 수 없습니다. ACL이든 읽기 전용 속성이든 디스크가 꽉 찼든 할당량이든 보안 제품이 앞을 막고 있든, **실제 저장을 결정할 바로 그것이 이 답도 결정합니다.** 기존 파일을 건드리지 않도록 `O_EXCL`로 만들고, pid와 시각을 이름에 넣어 두 세션이 부딪히지 않게 하고, 성공하든 실패하든 지웁니다. **두 셸 모두** 같은 이유로 같은 방식으로 바꿨습니다.

덤으로, 이 저장소가 오랫동안 *"root라서 시험할 수 없다"*고 기록해 온 경우를 **처음으로 실제 시험**하게 되었습니다. 권한 없는 사용자로 내려가 쓸 수 없는 폴더에 탐침을 시도하면 거부되는 것을 확인합니다.

```
ok    the probe says NO to a folder an unprivileged user cannot write
      (NR-DEP-09, exercised at last)
ok    and it left nothing in a folder it could not write
```

### ✅ 실사용 중 발견 — 점검이 앱을 **실행해 버려** 배포본이 만들어지지 않았습니다

준비 담당자가 매뉴얼대로 `python tools\bundle_runtime.py ... --zip` 을 돌렸더니, **앱이 저절로 뜨고 이름 입력 화면이 나왔으며, 만들어졌어야 할 배포용 압축 파일은 없었습니다.**

**제가 넣은 결함입니다.** 런타임을 넣은 뒤 "이 파이썬으로 앱이 실제로 뜨는가"를 확인하려고 `PM_APP.py --version` 을 물었는데, **그 옵션이 앱에 없었습니다.** 앱은 모르는 단어를 조용히 무시하도록 만들어져 있어서, 대답하는 대신 **평소처럼 시작**했습니다 — 서버를 열고 브라우저를 띄우고 사람을 기다렸습니다. 시작한 앱은 돌아오지 않으므로 120초 뒤 시간 초과 예외가 났고, 그 예외를 아무도 잡지 않아 **압축을 만드는 대목에 닿기도 전에 스크립트가 죽었습니다.**

**이것이 시험을 빠져나간 이유가 결함 자체보다 중요합니다.** 그 줄은 `if os.name == "nt"` 안에 있었습니다 — **윈도우에서만 실행되는 가지**입니다. 제 시험은 리눅스에서 도는데, 그래서 **그 줄은 단 한 번도 실행된 적이 없었습니다.** 41개 스위트가 모두 통과한 채로 나간 이유가 이것입니다. 시험이 약했던 것이 아니라, **시험이 닿을 수 없는 곳에 코드를 둔 것**이 잘못입니다.

**고친 방향 — 같은 부류가 다시는 숨지 못하게**

| 무엇 | 어떻게 |
|---|---|
| `--version` 을 **진짜 옵션으로** 만듦 | 버전만 찍고 즉시 끝납니다. 서버도, 브라우저도, 데이터 폴더도 건드리지 않습니다. 그래서 **"이 파이썬으로 앱이 뜨는가"를 앱을 띄우지 않고** 물을 수 있습니다 |
| 점검을 `verify(파이썬, 앱폴더)` 함수로 분리 | **파이썬 경로를 인자로 받습니다.** 윈도우에서는 동봉 런타임을, 시험에서는 지금 돌고 있는 파이썬을 넘깁니다 — 어느 OS에서도 실행되는 코드가 되었습니다. 이것이 근본 원인에 대한 처방입니다 |
| 모든 점검에 시간 제한 + 예외 포착 | 멈춘 점검은 이제 **예외가 아니라 한 줄의 답**입니다: `no answer in 60 seconds - it did not stop by itself` |
| 낡은 빌드는 **묻지 않음** | 폴더 안의 앱이 `--version` 을 모르는 구버전이면 아예 묻지 않습니다. 물으면 또 실행되기 때문입니다 |
| 압축은 **점검과 무관하게** 수행 | 점검이 실패해도 압축 파일은 만들어집니다. 실패는 **맨 마지막 줄** `NOT READY TO HAND OUT` 으로 말하고 종료 코드 1을 남깁니다 — 알리는 것과 못 만들게 하는 것은 다릅니다 |

원래 사고를 **그대로 재현**해 확인했습니다. 앱을 흉내 낸 "끝나지 않는" 프로그램을 물었을 때, 이제는 죽지 않고 60초 뒤 이렇게 답한 뒤 압축까지 마칩니다.

```
START     NO - no answer in 60 seconds - it did not stop by itself, so it was stopped
...
  NOT READY TO HAND OUT: START did not pass. The folder
  and any zip above were still written, so nothing is lost
```

시험 8건을 이 사고의 모양 그대로 추가했습니다 — 점검이 **여기서 호출될 수 있는가**, 넷 모두 **스스로 돌아오는가**(0.1초), 멈춤이 **예외가 아니라 답인가**, 낡은 빌드를 **시작하지 않고 건너뛰는가**, 실패해도 **압축이 남는가**.

```
test_no_python     FAILURES: none   (42개 검사, 이번에 14개 추가)
전체 41개 스위트   41 통과 · 0 실패
```

**그리고 같은 부류가 하나 더 있었습니다 — 바로 다음 단계에서 나왔습니다.** 담당자가 배포본을 만든 뒤 절차서가 시키는 대로 `python tools\test_python_app.py` 를 돌리자 이번에는 **`ModuleNotFoundError: No module named 'playwright'`** 로 끝났습니다.

**앱의 문제가 아닙니다.** 그 시험은 절반이 **진짜 브라우저를 몰아서** 화면의 숫자를 참조 구현과 대조하는 것이고, 그 브라우저를 다루는 도구가 담당자 PC에 없었습니다. **앱 자체는 표준 라이브러리 외에 아무것도 요구하지 않습니다**(NR-DEP-05, `test_layers.py` 가 강제). 그러나 **증상이 그렇게 보이지 않는 것**이 문제였습니다 — 화면에 뜬 것은 빨간 traceback이었고, 그것은 "앱이 고장났다"처럼 읽힙니다.

**더 나빴던 것은, 그 한 줄 때문에 브라우저가 필요 없는 나머지 절반도 못 돌았다는 점입니다.** 소켓·키·외부 출처 거부·DNS 리바인딩 거부·디스크 노출 금지 — 열두 가지 검사가 `import` 한 줄 때문에 시작조차 못 했습니다. 게다가 그 파일은 **리눅스 크로미움 경로를 코드에 박아** 두고 있어서, 윈도우에서는 playwright를 설치해도 돌지 않았을 것입니다. **이번에도 "내 기계에서만 돌아가는 코드"였습니다.**

| 무엇 | 어떻게 고쳤는가 |
|---|---|
| `playwright` 를 **늦게 가져옴** | 없으면 `None` 으로 두고 진행합니다. **시험 도구가 없는 것과 앱이 고장난 것은 다릅니다** |
| 브라우저 경로를 **찾아서** 씀 | 박아 둔 리눅스 경로 대신 `PM_APP_CHROME` → 알려진 경로 → playwright 자신의 선택 순서. 윈도우에서도 성립합니다 |
| **절반은 그대로 수행** | 브라우저 없이도 12건이 실제로 돕니다. 여기에 "시작만으로 아무것도 흘리지 않았다"는 검사 2건을 더했습니다 |
| **부분 수행을 부분이라고 말함** | `PARTIAL RUN` 과 **종료 코드 2** — 실패(1)도 통과(0)도 아닙니다. 화면이 `pip install playwright` 와, pip을 못 쓰는 경우 **대신 돌릴 두 가지**를 알려 줍니다 |
| `--no-browser-checks` | 절반만 일부러 돌리는 방법. 시험이 이 경로를 검사합니다 |

```
python tools/test_python_app.py --no-browser-checks
  ok   no key, no answer                       HTTP 403   (외 11건)
  SKIP every check below needs a browser
  PARTIAL RUN ... 0 failed          종료 코드 2
```
