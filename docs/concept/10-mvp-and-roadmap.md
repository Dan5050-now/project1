# 10. MVP 범위와 로드맵

## 1. 단계 구분의 원칙

로드맵은 [04](04-domain-concepts.md) 7장의 도메인 의존 관계에서 도출합니다. 임의로 나누지 않습니다.

```
D2 RTSM ──┬──> D1 EDC ──> D3 SDV
          ├──> D4 Sample
          └──> D5 Image        모두 ──> D6 Timeline
```

**D2가 뿌리입니다.** 피험자와 방문이 없으면 어떤 도메인의 expected도 만들 수 없습니다. 따라서 D2를 가장 먼저 만들고, 그 위에 D1을 얹어 **엔진이 실제로 작동하는지 검증**합니다. 이것이 Phase 1의 목표입니다.

D3와 D6은 다른 도메인의 산출을 소비하므로 나중에 옵니다.

## 2. Phase 0 — 기반 (Foundation)

**목표.** 업무 기능 없이 플랫폼 뼈대만 세웁니다. 이 단계가 부실하면 이후 전부가 흔들립니다.

| 항목 | 산출 |
|---|---|
| 프로젝트 구조 | [09](09-tech-stack.md) 3.5의 모듈 구조 |
| 마스터 데이터 | Trial, Country, Site, Subject, Visit |
| 인증·RBAC | SSO 연동, 3차원 권한 모델, 역할 템플릿 |
| 관리자 화면 | 사용자·역할·배정 관리 (요구사항 C2) |
| 감사 추적 | 전 모델 적용, 조회 화면 (요구사항 C3) |
| 유입 기반 | SourceSystem, Feed, MappingProfile, DataDrop, 검증 파이프라인 |
| 스냅샷 | 스냅샷 생성과 시점 조회 (요구사항 C4) |
| Export 기반 | 모든 테이블 CSV/Excel export (요구사항 C5) |

**완료 조건.** 관리자가 사용자를 만들고 역할을 배정할 수 있고, 사용자가 SSO로 로그인해 자신의 권한 범위 안의 시험만 볼 수 있으며, 마스터 데이터를 엑셀로 업로드하고 그 변경이 감사 로그에 남는다.

## 3. Phase 1 — 엔진 검증 (D2 + D1)

**목표.** Expectation Engine과 Progress Engine이 실제 데이터에서 작동함을 증명합니다. **이 단계가 프로젝트 전체의 성패를 가릅니다.**

| 항목 | 산출 |
|---|---|
| 가정 관리 | AssumptionSet, SoA, VisitSchedule, StageScopeRule 입력·버전 관리 |
| Expectation Engine | 방문 전개, 기대 항목 생성 (확정분) |
| D2 RTSM | 피험자 상태, 층화, 예정/실제 방문, 윈도우 이탈 |
| D1 EDC | 7단계 진척, 쿼리 현황 |
| Progress Engine | 매칭, 단계 상태 갱신, backlog·rate·aging |
| 롤업 | trial / country / site / subject 4단계 |
| 도메인 화면 | [05](05-information-architecture.md) 3.3 공통 레이아웃, 드릴다운 |
| Subject 360 | D1 + D2 범위 |
| 지표 정의 등록부 | [08](08-platform-services.md) 6장 |

**완료 조건.** 실제 시험 하나의 RTSM·EDC 리포트를 업로드하면, 화면의 입력률·SDV율이 담당자가 엑셀로 만든 숫자와 **일치**한다. 불일치가 있으면 그 원인을 드릴다운으로 설명할 수 있다.

> **이 완료 조건이 가장 중요합니다.** 숫자가 기존 방식과 다르면 사람들은 앱을 믿지 않습니다. Phase 1은 기능을 넓히는 단계가 아니라 **신뢰를 얻는 단계**입니다.

## 4. Phase 2 — 도메인 확장 (D4 + D5 + D3)

**목표.** 검증된 엔진 위에 나머지 도메인을 얹습니다. 아키타입 설계가 옳았다면 이 단계는 **설정 추가에 가까워야** 합니다. 만약 도메인마다 엔진을 고쳐야 한다면 [03](03-core-concept-model.md)의 설계를 재검토해야 한다는 신호입니다.

| 항목 | 산출 |
|---|---|
| D4 Sample | 단계 체인, 다단계 식별자 매칭, 이슈, 분석 상태 |
| D5 Image | 단계 체인, QC 실패 추적, 판독 상태 |
| Reconciliation Center | 4종 불일치 통합 작업 목록 |
| Issue 관리 | 쿼리·샘플·영상 이슈 통합, 차단 관계 |
| D3 SDV Plan | 방문 계획 CRUD, 상태 전이, CRA 리소스 |
| 예측 Layer 2 | 등록 예측, backlog 소진 예측, 도착 지연 모델 |
| SDV 적정성 평가 | [04](04-domain-concepts.md) 3.3 |
| Subject 360 확장 | 전 도메인 |
| Portfolio 화면 | 다중 시험 뷰 |

**완료 조건.** 샘플 한 건이 어느 단계에서 멈췄는지 화면에서 즉시 확인되고, SDV 계획의 적정성 판정이 실무자 판단과 부합한다.

## 7. 로드맵 요약

```
Phase 0  기반            ████                 플랫폼 뼈대, 업무 기능 없음
Phase 1  엔진 검증        ████████             D2 + D1 — 성패의 분기점
Phase 2  도메인 확장      ██████               D4 + D5 + D3 + 예측
Phase 3  타임라인·통합    █████                D6 + KRI + BI 연동
Phase 4  고도화           ████                 커넥터, 학습 모델, validation
```

기간은 개발 인력 규모가 확정된 뒤에 산정합니다 (DP-09-5).

## 8. 단계별 검증 방법

각 Phase는 **실제 시험 데이터로 검증**합니다. 합성 데이터로만 검증하면 실무의 지저분함(식별자 불일치, 형식 변동, 예외 상황)을 놓칩니다.

| Phase | 검증 방법 |
|---|---|
| 0 | 권한 시나리오 테스트 — 각 역할로 로그인해 보이는 범위 확인 |
| 1 | **기존 엑셀 리포트와 숫자 대조** (완료 조건) |
| 2 | 실제 vendor 리포트 3종 이상으로 매칭률 확인 |
| 3 | 과거 시험의 마일스톤 이력으로 `AT_RISK` 판정 정확도 역검증 |

## 9. 초기 대상 시험 선정

Phase 1의 검증 대상으로 **어떤 시험을 쓸 것인가**가 중요합니다.

| 기준 | 권고 |
|---|---|
| 규모 | 중간 규모 (사이트 10~30개). 너무 작으면 문제가 안 드러나고, 너무 크면 성능 문제에 발목 |
| 진행 단계 | **등록 진행 중** — expected와 actual이 모두 활발히 발생 |
| 데이터 가용성 | RTSM·EDC 리포트를 정기적으로 받고 있을 것 |
| 담당자 | 기존 엑셀 리포트를 만드는 담당자가 **검증에 참여 가능**할 것 |

마지막 기준이 가장 중요합니다. 비교 기준이 되는 "정답"을 만드는 사람이 곁에 없으면 Phase 1의 완료 조건을 판정할 수 없습니다.
