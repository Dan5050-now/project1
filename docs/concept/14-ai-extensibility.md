# 14. AI 활용 확장성

*검토 반영 신규 문서 (요구사항 9, 10)*
*v2: **내부 LLM 연결**로 전제 확정 (DP-14-3)*

이 문서는 앱에 AI를 결합하기 위한 **구조**를 정의합니다.

**연결 대상은 사내 내부 LLM으로 확정되었습니다.** 이에 따라 임상 데이터가 조직 경계를 벗어나지 않으며, 외부 전송에 따르던 제약이 사라집니다. 다만 모델 교체 가능성과 통제·기록 지점 확보를 위해 **제공자 어댑터 계층은 그대로 유지**합니다. 내부 LLM도 버전이 바뀌고, 언젠가 다른 모델로 교체될 수 있기 때문입니다.

## 1. 기본 원칙

AI를 규제 대상 업무 도구에 결합할 때 가장 위험한 실패는 **AI가 무엇을 했는지 설명할 수 없게 되는 것**입니다. 다음 네 원칙으로 그 위험을 차단합니다.

### 1.1 원칙 1 — AI는 보고되는 숫자를 계산하지 않는다

이것이 가장 중요한 원칙입니다.

지표 계산은 [15](15-metric-specification.md)에 명세된 **결정론적 엔진**이 수행합니다. AI는 이상을 탐지하고, 원인을 설명하고, 매핑을 제안하고, 초안을 작성할 수 있지만, **화면에 표시되고 보고서에 들어가는 숫자를 만들지는 않습니다.**

이유는 재현 가능성입니다. AI의 출력은 동일 입력에 대해 동일 결과를 보장하기 어렵습니다. 재현되지 않는 숫자는 GCP와 computerised system validation 관점에서 근거가 될 수 없습니다.

```
┌──────────────────────────────────────────────────────────┐
│  결정론 영역 (AI 금지)          │  AI 영역                 │
├──────────────────────────────────┼──────────────────────────┤
│  지표 계산                        │  이상 탐지와 설명         │
│  기대 항목 생성                   │  매핑 제안               │
│  단계 상태 판정                   │  검증 규칙 제안           │
│  Reconciliation 매칭 판정         │  불일치 원인 분류 제안    │
│  기한 계산                        │  요약과 초안 작성         │
└──────────────────────────────────┴──────────────────────────┘
```

### 1.2 원칙 2 — AI는 사전 정의된 작업만 수행한다

AI가 임의로 데이터베이스를 조작할 수 있게 하지 않습니다. **등록된 작업(Registered Task) 목록 안에서만** 동작하며, 각 작업은 입력·출력·권한이 명세되어 있습니다.

### 1.3 원칙 3 — 모든 AI 행위는 사람과 구분되어 기록된다

요구사항 10의 직접적 구현입니다. 감사 추적에서 **누가 사람이고 누가 AI인지, 어느 AI 작업의 결과인지**가 명확히 남습니다.

### 1.4 원칙 4 — 쓰기는 기본이 제안이다

AI가 데이터를 직접 바꾸는 것은 **명시적으로 허용된 작업에 한정**합니다. 기본 동작은 **제안(proposal)** 을 만들고 사람이 승인하는 것입니다.

## 2. AI 권한 모델

요구사항 9가 언급한 "계산만 / 데이터 수정 / 데이터 생성" 구분을 권한 등급으로 정의합니다.

| 등급 | 코드 | 허용 행위 | 승인 |
|---|---|---|---|
| 1 | `READ_ONLY` | 조회만. 출력은 화면 표시나 설명 | 불필요 |
| 2 | `ANALYZE_ONLY` | 조회 + 분석 결과 생성 (이상 탐지, 분류, 요약). **원본 데이터 불변** | 불필요 |
| 3 | `PROPOSE` | 변경 제안 생성. 실제 반영은 사람이 승인 | **사람 승인 필수** |
| 4 | `DATA_UPDATE` | 지정된 필드의 기존 값 수정 | 작업별 설정 |
| 5 | `DATA_CREATE` | 새 레코드 생성 (이슈 등록, 불일치 항목 생성 등) | 작업별 설정 |

권한은 **AI 에이전트별 × 작업별 × 데이터 범위별**로 부여됩니다. 사람 사용자의 3차원 권한 모델([08](08-platform-services.md) 2.1)과 동일한 구조입니다.

```
AI 권한 = 에이전트 × 등록된 작업 × 데이터 범위 × 권한 등급
```

> **설계 규칙.** AI 에이전트의 권한은 **그것을 실행시킨 사람의 권한을 넘을 수 없습니다.** CRA가 실행한 AI 작업이 그 CRA가 볼 수 없는 사이트의 데이터에 접근하지 못합니다. 눈가림 마스킹도 동일하게 적용됩니다.

## 3. 등록된 작업 (Registered Task)

AI가 수행할 수 있는 작업을 사전에 등록합니다. 각 작업은 다음을 명세합니다.

| 항목 | 내용 |
|---|---|
| `task_code` | 작업 식별자 |
| `description` | 무엇을 하는 작업인가 |
| `required_level` | 필요한 권한 등급 (2장) |
| `input_schema` | 입력 데이터의 구조 |
| `output_schema` | 출력 결과의 구조 |
| `approval_required` | 사람 승인 필요 여부 |
| `deterministic_fallback` | AI 미사용 시의 대체 동작 |
| `version` | 작업 정의 버전 |

`deterministic_fallback`이 중요합니다. **AI가 없어도 앱은 동작해야 합니다.** AI는 보조 수단이지 필수 구성 요소가 아닙니다.

### 3.1 초기 작업 목록

#### Import 검증 보조 (요구사항 9 전반부)

[12](12-standard-source-templates.md) 5장의 체크포인트를 AI가 수행하거나 보강합니다.

| `task_code` | 내용 | 등급 |
|---|---|---|
| `import.anomaly_detect` | 업로드 데이터에서 통계적 이상 탐지 (행 수 급변, 분포 이탈, 특정 사이트 누락) | `ANALYZE_ONLY` |
| `import.consistency_explain` | 일관성 위반 건에 대해 가능한 원인 설명 생성 | `ANALYZE_ONLY` |
| `import.mapping_suggest` | 원본 컬럼명을 표준 컬럼에 매핑하는 후보 제안 | `PROPOSE` |
| `import.codelist_suggest` | 미등록 코드값에 대한 매핑 후보 제안 | `PROPOSE` |
| `import.rule_suggest` | 반복 발생하는 오류 패턴에 대한 신규 검증 규칙 제안 | `PROPOSE` |

> **경계.** `import.anomaly_detect`는 **결정론적 규칙이 놓친 것을 찾는 보조 수단**입니다. [12](12-standard-source-templates.md) 5장의 규칙 기반 검증을 대체하지 않습니다. 규칙 검증이 1차이고 AI가 2차입니다.

#### Reconciliation 보조

| `task_code` | 내용 | 등급 |
|---|---|---|
| `recon.cause_classify` | 불일치 건의 추정 원인 분류 (식별자 오류 / 배송 지연 / EDC 미입력 등) | `ANALYZE_ONLY` |
| `recon.match_suggest` | `AMBIGUOUS_MATCH` 건의 매칭 후보 제안 | `PROPOSE` |
| `recon.issue_draft` | 불일치 건에 대한 이슈 초안 생성 | `PROPOSE` |

매칭 **판정**은 결정론적 엔진이 하고, AI는 모호한 건의 **후보를 제안**만 합니다 (원칙 1.1).

#### 진척 분석 보조

| `task_code` | 내용 | 등급 |
|---|---|---|
| `progress.narrative` | 계산된 지표를 바탕으로 주간 리뷰용 서술 요약 생성 | `ANALYZE_ONLY` |
| `progress.root_cause` | 지표 악화의 가능한 원인을 데이터에서 탐색해 제시 | `ANALYZE_ONLY` |
| `progress.site_insight` | 사이트별 패턴 설명 | `ANALYZE_ONLY` |

이 작업들은 **이미 계산된 숫자를 설명**할 뿐 숫자를 만들지 않습니다.

#### 데이터 작업 (제한적)

| `task_code` | 내용 | 등급 | 승인 |
|---|---|---|---|
| `data.issue_create` | 탐지된 문제에 대해 이슈 레코드 생성 | `DATA_CREATE` | 설정 가능 |
| `data.discrepancy_annotate` | 불일치 건에 분류·코멘트 추가 | `DATA_UPDATE` | 설정 가능 |
| `data.task_status_update` | 타임라인 task 상태 갱신 제안 | `PROPOSE` | 필수 |

**지표 값, 기대 항목, 단계 상태, 설정 값은 AI가 수정할 수 있는 대상이 아닙니다.** 이들은 결정론 영역이며, AI 권한 모델에서 원천적으로 제외됩니다.

## 4. 통합 구조

### 4.1 계층

```
┌─────────────────────────────────────────────────────────┐
│  AI Gateway                                              │
│  - 작업 라우팅                                            │
│  - 권한 검사 (에이전트 × 작업 × 범위 × 등급)               │
│  - 입출력 스키마 검증                                      │
│  - 실행 기록 생성                                          │
└───────┬─────────────────────────────────┬────────────────┘
        │                                 │
┌───────▼──────────┐            ┌─────────▼────────────────┐
│  Tool API        │            │  AI Provider Adapter     │
│  (앱이 노출)      │            │  (외부 AI 서비스 연결)     │
│                  │            │                          │
│  read_metrics    │            │  제공자 중립 인터페이스    │
│  read_items      │            │  - 요청/응답 정규화        │
│  read_drops      │            │  - 재시도·타임아웃         │
│  create_issue    │            │  - 토큰·비용 기록          │
│  update_discrep  │            │                          │
│  propose_change  │            │                          │
└──────────────────┘            └──────────────────────────┘
```

### 4.2 Tool API

AI가 앱의 데이터에 접근하는 유일한 경로입니다. **직접 DB 접근은 허용하지 않습니다.**

| Tool | 등급 | 설명 |
|---|---|---|
| `read_metrics` | 1 | 계산된 지표 조회 (좌표 지정 필수) |
| `read_items` | 1 | 개별 항목·단계 상태 조회 |
| `read_issues` | 1 | 이슈 조회 |
| `read_discrepancies` | 1 | 불일치 조회 |
| `read_data_drop` | 1 | 업로드 원본 데이터 조회 (검증 작업용) |
| `read_config` | 1 | 시험 설정 조회 |
| `create_issue` | 5 | 이슈 생성 |
| `update_discrepancy` | 4 | 불일치 건 분류·코멘트 갱신 |
| `create_proposal` | 3 | 변경 제안 생성 (승인 대기열로) |

각 Tool은 호출 시 **권한 검사를 통과해야 하며, 모든 호출이 기록**됩니다. 읽기 호출도 기록 대상입니다.

### 4.3 내부 LLM 연결 (DP-14-3 확정)

연결 대상은 **사내 내부 LLM**입니다. 데이터가 조직 경계를 벗어나지 않으므로 설계가 다음과 같이 달라집니다.

| 항목 | 외부 서비스였다면 | **내부 LLM (확정)** |
|---|---|---|
| 데이터 전송 범위 | 최소화 필요, 가명화 필수 | **제한 없음** — 조직 내부 |
| 식별자 마스킹 | 전송 전 필수 | **불필요** (눈가림 마스킹은 별개로 유지) |
| 시험별 전송 허용 설정 | 필요 | 불필요 |
| 데이터 보호 검토 | 별도 절차 필요 | 사내 정책 범위 내 |
| 응답 지연 | 네트워크 의존 | 내부 네트워크 |
| 비용 기록 | 과금 추적 필요 | 자원 사용량 기록 수준 |

**남는 제약은 두 가지입니다.** 첫째, 눈가림 마스킹은 여전히 적용됩니다. 내부라도 권한 없는 사람이 AI 출력을 통해 배정군을 알게 되면 안 되기 때문입니다. 둘째, AI 권한은 실행시킨 사람의 권한을 넘지 못합니다 (2장).

#### 어댑터 계층을 유지하는 이유

내부 LLM으로 확정되었어도 Provider Adapter를 없애지 않습니다.

| 이유 | 내용 |
|---|---|
| 모델 교체 | 내부 LLM도 버전이 바뀌고 교체됩니다. 모델 식별자가 감사 기록에 남아야 하므로([14](14-ai-extensibility.md) 5.2) 이 계층이 필요합니다 |
| 통제 지점 | 눈가림 마스킹과 권한 범위를 한 곳에서 강제 |
| 기록 지점 | 요청·응답·소요 시간·자원 사용을 한 곳에서 기록 |
| 장애 격리 | 내부 LLM이 응답하지 않을 때 `deterministic_fallback`으로 전환 (3장) |

#### 배포 고려사항

| 항목 | 내용 |
|---|---|
| 연결 방식 | 사내 네트워크 내 API 엔드포인트. 인증 방식은 사내 표준을 따름 |
| 가용성 | **앱은 내부 LLM이 없어도 동작해야 합니다.** 연결 실패는 AI 작업의 실패일 뿐 앱의 실패가 아닙니다 |
| 모델 버전 관리 | 모델 식별자와 버전을 `AI_TASK_RUN`에 기록 (5.2). 모델이 바뀌면 이전 실행 결과의 재현이 보장되지 않음을 명시 |
| 성능 | 대량 건(수천 행 이상) 처리는 배치로 분할. 실시간 화면 응답 경로에 두지 않음 |

## 5. 실행 기록과 감사 추적 (요구사항 10)

### 5.1 행위자 구분

감사 로그의 행위자를 세 종류로 구분합니다.

| `actor_type` | 의미 | 추가 기록 |
|---|---|---|
| `HUMAN` | 사람 사용자 | 사용자 ID |
| `AI` | AI 에이전트 | 에이전트 ID, 작업 코드, 실행 ID, 모델 식별자, 실행시킨 사람 |
| `ENGINE` | 앱 내부의 결정론적 엔진 | 엔진 이름, 실행 ID, 트리거 |

`ENGINE`을 `AI`와 분리한 것이 중요합니다. Expectation Engine의 기대 항목 생성은 자동화된 처리이지만 AI가 아니며, 완전히 재현 가능합니다. 이 둘을 섞으면 "AI가 만든 데이터"의 범위를 설명할 수 없게 됩니다.

### 5.2 AI 실행 기록 (AI Task Run)

AI 작업 한 번의 실행이 하나의 기록을 남깁니다.

| 항목 | 내용 |
|---|---|
| `run_id` | 실행 식별자 |
| `task_code` / `task_version` | 무슨 작업을 어느 버전으로 |
| `agent_id` | 어느 에이전트가 |
| `initiated_by` | 누가 실행시켰는가 (사람 또는 스케줄) |
| `provider` / `model_identifier` | 어느 서비스의 어느 모델로 |
| `started_at` / `finished_at` | **시각 기록** |
| `input_ref` | 입력 데이터의 참조 (스냅샷 ID, 필터 조건) |
| `output_ref` | 출력 결과의 저장 위치 |
| `tools_called` | 호출한 Tool 목록과 각 호출 기록 |
| `records_affected` | 영향받은 레코드 수와 식별자 |
| `status` | `SUCCEEDED` / `FAILED` / `REJECTED_BY_POLICY` |
| `human_review` | 승인자, 승인 시각, 승인/반려 결과 |

### 5.3 데이터 변경 기록

AI가 만든 모든 데이터 변경은 일반 감사 로그에 기록되며, **`actor_type = AI`와 `run_id`가 함께 남습니다.**

```
AuditLog:
  occurred_at    2026-09-18T09:14:22Z
  actor_type     AI
  actor_id       agent_recon_assistant
  ai_run_id      run_8f2a91
  initiated_by   user_kim (CDM Lead)
  action         CREATE
  entity_type    IssueObject
  entity_id      ISS-20260918-0042
  new_value      {...}
  reason         "recon.issue_draft: EDC_Y_NOT_RECEIVED 12건에 대한 이슈 생성"
  approved_by    user_kim
  approved_at    2026-09-18T09:20:05Z
```

이 구조로 다음 질문에 언제든 답할 수 있습니다.

- 이 레코드는 사람이 만들었는가 AI가 만들었는가
- AI가 만들었다면 누가 실행시켰고 누가 승인했는가
- 어느 작업 정의의 어느 버전으로 만들었는가
- 그때 입력은 무엇이었는가

### 5.4 조회 화면

관리자 화면에 **AI 활동 조회**를 별도로 둡니다.

| 조회 축 | 내용 |
|---|---|
| 실행 이력 | 작업별·에이전트별·기간별 실행 목록 |
| 영향 범위 | AI가 생성·수정한 레코드 목록 |
| 승인 대기 | 사람 승인을 기다리는 제안 목록 |
| 거부 이력 | 권한 정책에 의해 차단된 시도 |

## 6. 향후 validation 관점

현재는 non-GxP이지만, GCP와 computerised system validation 요건을 충족해야 할 때를 대비합니다.

| 요건 | 이 설계의 대응 |
|---|---|
| 시스템이 무엇을 하는지 명세되어야 함 | 등록된 작업 목록과 스키마 (3장) |
| 자동 처리의 결과가 재현 가능해야 함 | AI는 지표를 계산하지 않음 (원칙 1.1) |
| 변경의 행위자가 식별되어야 함 | `actor_type` 구분 (5.1) |
| 변경 이력이 보존되어야 함 | AI 실행 기록 + 감사 로그 (5.2, 5.3) |
| 사람의 통제가 유지되어야 함 | 기본 제안 방식 + 승인 절차 (원칙 1.4) |
| 시스템 없이도 업무가 가능해야 함 | `deterministic_fallback` (3장) |
| 데이터가 통제된 환경에 머물러야 함 | **내부 LLM 연결** (4.3) |

## 7. 단계적 도입

| Phase | 내용 |
|---|---|
| Phase 0~2 | **AI 없이 구축.** 단, Tool API와 권한 모델의 자리를 비워둠 |
| Phase 3 | Tool API 구현, `READ_ONLY`·`ANALYZE_ONLY` 작업 도입 (이상 탐지, 설명 생성) |
| Phase 4 | `PROPOSE` 작업 도입 (매핑 제안, 매칭 제안) + 승인 워크플로 |
| Phase 5 | 선택적으로 `DATA_CREATE`·`DATA_UPDATE` 작업 도입 |

AI를 나중에 붙이더라도 **Tool API와 감사 추적의 행위자 구분은 처음부터 설계에 포함**합니다. 이 둘은 나중에 얹을 수 없습니다.
