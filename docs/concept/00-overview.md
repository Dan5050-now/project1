# 00. 개요와 제품 비전

## 1. 문제 정의

### 1.1 현재 무엇이 문제인가

임상시험을 수행하는 동안 팀은 "**지금 무엇이 밀려 있는가**"를 알아야 합니다. 그런데 그 답은 한 시스템 안에 있지 않습니다. EDC에는 입력된 폼이 있고, RTSM에는 피험자와 방문이 있고, central lab 리포트에는 샘플이 있고, imaging vendor 리포트에는 이미지가 있습니다. 각각은 "무엇이 들어왔는지"만 알려줄 뿐, "**무엇이 들어왔어야 하는지**"는 알려주지 않습니다.

그래서 현장에서는 다음과 같은 일이 반복됩니다.

- 담당자가 매주 여러 시스템에서 리포트를 내려받아 엑셀에서 수작업으로 대조합니다.
- 기대치(expected)는 개인이 만든 엑셀 수식 안에만 존재하고, 그 가정이 무엇이었는지 시간이 지나면 아무도 재현하지 못합니다.
- 도메인마다 담당자가 달라 EDC 담당자, biomarker 담당자, imaging 담당자가 각자 다른 숫자를 들고 회의에 들어옵니다.
- 문제가 이미 커진 뒤에야 발견됩니다. 밀리고 있다는 사실은 알지만, **언제 정상화되는지**는 아무도 예측하지 못합니다.

### 1.2 이 앱이 해결하려는 것

이 앱의 본질은 **기대치를 시스템의 1급 데이터로 만드는 것**입니다.

지금까지 "expected"는 엑셀 수식이었습니다. 이 앱에서는 expected가 **가정(assumption)에서 규칙에 따라 생성되고, 버전이 붙고, 감사 추적이 남으며, 실적과 자동으로 대조되는 데이터**가 됩니다. 이것이 단순 대시보드와 이 앱을 가르는 핵심 차이입니다.

```
         [가정]                    [실적]
  프로토콜 SoA, 등록 계획          EDC 폼, lab 리포트
  RTSM 피험자·방문                 imaging 리포트, vendor 파일
        │                            │
        ▼                            ▼
  ┌──────────────┐            ┌──────────────┐
  │ Expectation  │            │  Ingestion   │
  │   Engine     │            │    Layer     │
  └──────┬───────┘            └──────┬───────┘
         │  expected (분모)          │  actual (분자)
         └────────────┬──────────────┘
                      ▼
            ┌───────────────────┐
            │  Progress Engine  │
            │  backlog / rate   │
            │  aging / forecast │
            └─────────┬─────────┘
                      ▼
        trial → country → site → subject
```

## 2. 제품 비전

> **한 문장:** 임상시험에서 앞으로 나와야 할 모든 것을 가정 기반으로 예측하고, 실제로 들어온 것과 대조하여, 무엇이 얼마나 밀려 있고 언제 해소되는지를 하나의 화면에서 답하는 시스템.

### 2.1 이 앱이 답해야 하는 질문

이 앱이 성공했는지는 다음 질문에 몇 초 안에 답할 수 있는가로 판단합니다.

| 질문 | 관련 도메인 |
|---|---|
| 지금 우리 시험에서 가장 많이 밀린 사이트는 어디이고, 무엇이 밀려 있는가 | 전체 |
| 이 사이트의 이 피험자는 3차 방문을 했는데 왜 데이터가 안 들어왔는가 | EDC + RTSM |
| 다음 DBL까지 남은 backlog를 현재 속도로 소진할 수 있는가 | EDC + Timeline |
| 이번 분기 CRA 방문 계획이 SDV 부하를 감당하기에 충분한가 | SDV + EDC |
| 지난주 채취된 샘플 중 central lab에 아직 도착하지 않은 것은 무엇인가 | Sample |
| BICR 판독이 밀린 원인이 업로드 지연인가 QC 실패인가 | Image |
| 우리가 milestone을 놓치고 있다면, 어느 task가 원인인가 | Timeline |

### 2.2 이 앱이 하지 않는 것 (Non-goals)

범위를 명확히 하기 위해 **의도적으로 제외**하는 것을 먼저 적습니다.

| 제외 항목 | 이유 |
|---|---|
| EDC를 대체하는 데이터 수집 | 이 앱은 source가 아니라 **tracking layer**입니다. CRF 입력은 EDC에서 합니다. |
| 쿼리 발행·응답 | 쿼리의 **집계와 추적**은 하지만, 발행·응답은 EDC에서 합니다. |
| SDTM/ADaM 변환, 통계 분석 | submission 데이터 파이프라인은 별도 영역입니다. |
| 규제 제출용 기록 보관 | 초기 단계는 non-GxP입니다. 원본 기록은 각 source system이 보유합니다. |
| BI 대시보드 도구 대체 | 고급 시각화는 외부 도구가 더 낫습니다. 이 앱은 **정제된 데이터를 내보내는 쪽**입니다. |

이 경계는 중요합니다. 이 앱은 **source of record가 아니라 source of truth about progress**입니다.

## 4. 설계 원칙

개념 설계 전체를 관통하는 7가지 원칙입니다. 이후 모든 설계 판단은 이 원칙으로 정당화됩니다.

### 4.1 하나의 커널, 여러 도메인

여섯 도메인은 서로 달라 보이지만 실제로는 **네 가지 아키타입의 반복**입니다 (→ [03](03-core-concept-model.md)). 도메인마다 별도 로직을 만들지 않고, 공통 커널 위에 도메인 어댑터를 얹습니다. 이것이 유지보수 비용을 결정합니다.

### 4.2 기대치는 규칙에서 생성되고 버전을 가진다

expected는 사람이 입력한 숫자가 아니라 **가정 + 규칙의 계산 결과**입니다. 가정이 바뀌면 expected가 다시 계산되고, 어느 가정 버전으로 계산했는지가 항상 기록됩니다.

### 4.3 모든 숫자는 근거까지 내려갈 수 있어야 한다

trial 레벨의 `entry rate 87%`를 클릭하면 국가, 사이트, 피험자를 거쳐 **결국 개별 폼 한 줄까지** 도달해야 합니다. 드릴다운이 끊기는 지표는 신뢰받지 못하고 결국 쓰이지 않습니다.

### 4.4 모든 리포트는 재현 가능해야 한다

"지난주 화요일 회의에서 본 그 숫자"를 언제든 다시 만들 수 있어야 합니다. 이를 위해 모든 지표는 `(데이터 스냅샷 버전, 가정 버전)` 조합에 대해 계산되며, 그 조합은 화면에 항상 표시됩니다.

### 4.5 진행 중인 것과 밀린 것을 구분한다

이것은 흔히 놓치는 지점입니다. 방문이 어제 일어난 피험자의 미입력 폼과 3주 전 방문의 미입력 폼은 **같은 backlog가 아닙니다**. 기대 시점(due date)과 유예 기간(grace period)을 개념에 내장하여 `아직 기한 내(pending)` 와 `기한 초과(overdue)` 를 분리합니다 (→ [03](03-core-concept-model.md) 3.4).

### 4.6 눈가림(blinding)은 권한 모델의 일부다

층화 정보, 배정군, 일부 lab 결과는 눈가림 대상일 수 있습니다. 권한 모델은 "어느 모듈을 보는가"뿐 아니라 "**어느 필드를 마스킹하는가**"까지 포함해야 합니다. 나중에 얹으면 반드시 사고가 납니다.

### 4.7 데이터를 가두지 않는다

앱이 계산한 모든 지표는 표준 형식으로 내보낼 수 있어야 합니다. 사용자가 Power BI나 Tableau에서 이 앱의 데이터를 쓰는 것을 **정상 사용 방식으로 간주**합니다.
