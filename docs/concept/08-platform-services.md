# 08. 플랫폼 공통 서비스

이 문서는 요구사항 "Consideration for the app"의 b~f를 개념으로 정의합니다. 이 부분은 업무 기능처럼 눈에 띄지 않지만, **나중에 얹을 수 없어서** 개념 단계에서 확정해야 하는 영역입니다.

*개정 이력: v2 (검토 반영 — 행위자 구분, 설정 버전, 표준 template 연계)*

## 1. 인증 (Authentication)

| 항목 | 개념 |
|---|---|
| 로그인 | 사내 SSO(SAML/OIDC) 우선, 자체 계정은 대체 수단 |
| 세션 | 만료 시간 설정, 비활동 자동 로그아웃 |
| 다중 인증 | SSO에 위임. 자체 계정 사용 시 TOTP 옵션 |
| 계정 생명주기 | 생성·비활성화·재활성화. **삭제는 하지 않음** (감사 추적 무결성) |

계정을 삭제하지 않는다는 결정이 중요합니다. 삭제하면 과거 감사 로그의 행위자를 특정할 수 없게 됩니다.

## 2. 권한 (Authorization) — 요구사항 C2

### 2.1 3차원 권한 모델

요구사항은 "역할이 각 정보에 대한 접근을 허용하고, 접근 권한(read-only, write)이 구분된다"고 했습니다. 실무에서는 여기에 **데이터 범위** 차원이 반드시 필요합니다. 같은 CRA 역할이라도 담당 국가만 봐야 하기 때문입니다.

```
            ┌─────────────────────────────────────┐
            │  권한 = 모듈 × 접근수준 × 데이터범위 │
            └─────────────────────────────────────┘

  모듈:      D1 EDC / D2 RTSM / D3 SDV / D4 Sample / D5 Image / D6 Timeline
             / Reconciliation / Assumptions / Export / Admin

  접근수준:  NONE  <  READ  <  WRITE

  데이터범위: 전체 / 특정 시험 / 특정 국가 / 특정 사이트
```

### 2.2 역할 (Role)

역할은 권한의 묶음입니다. 관리자가 자유롭게 정의할 수 있게 하되, [02](02-personas-and-use-cases.md) 3장의 매트릭스를 **기본 템플릿**으로 제공합니다. 새 시험을 시작할 때 템플릿에서 역할을 복제하면 설정 부담이 크게 줄어듭니다.

### 2.3 사용자 배정

```
User ──┬── UserRole(role=CDM Lead, scope=Trial ABC-301)
       └── UserRole(role=Viewer,    scope=Trial XYZ-201, country=KR)
```

한 사용자가 시험마다 다른 역할을 가질 수 있어야 합니다. 이것은 실무에서 매우 흔합니다.

### 2.4 눈가림 마스킹 (설계 원칙 4.6)

모듈·범위와 **직교하는 별도 축**입니다.

| 마스킹 대상 후보 | 필드 |
|---|---|
| 배정군 | treatment arm |
| 층화 인자 | stratification factors |
| 일부 lab 결과 | 눈가림 해제 가능 검사값 |
| RTSM kit 정보 | kit type |

`Permission.unblinded = true`인 사용자만 실제 값을 봅니다. 그 외에는 `[마스킹됨]`으로 표시되며, **export에서도 동일하게 마스킹**됩니다. export 경로에서 마스킹이 빠지는 것이 전형적인 사고 유형이므로, 마스킹은 조회 계층이 아니라 **데이터 접근 계층에서 한 번만** 적용되도록 설계합니다.

### 2.5 관리자 화면 (요구사항 C2 후단)

요구사항이 명시한 대로 시스템 관리자 전용 탭을 둡니다.

| 화면 | 기능 |
|---|---|
| Users | 계정 목록, 생성, 비활성화, 역할 배정 |
| Roles & Permissions | 역할 정의, 모듈별 접근 수준 설정 |
| Trial Assignments | 사용자-시험-역할-범위 배정 |
| Audit Trail Viewer | 감사 로그 검색 (3장) |
| System Settings | 전역 설정, 소스 시스템 등록 |

**관리자는 업무 데이터에 기본 접근 권한이 없습니다.** 권한을 관리하는 사람과 데이터를 보는 사람을 분리하는 것이 통제의 기본입니다.

## 3. 감사 추적 (Audit Trail) — 요구사항 C3

### 3.1 요구 수준

벤치마크([01](01-benchmark.md) 2.4)에서 확인한 21 CFR Part 11 Subpart B의 요구는 명확합니다. 전자 기록을 **생성·수정·삭제**하는 조작자의 입력과 행위에 대해 **안전하고, 컴퓨터가 생성하며, 시각이 찍힌** 감사 추적을 독립적으로 기록해야 합니다. FDA는 변경뿐 아니라 **최초 입력(create)도 기록**할 것을 요구합니다.

지금은 non-GxP이지만, 확정된 전제("Part 11 대비 설계")에 따라 **스키마와 기록 범위는 처음부터 이 수준을 만족**시킵니다.

### 3.2 기록 항목

| 항목 | 내용 |
|---|---|
| **행위자 유형** | **`HUMAN` / `AI` / `ENGINE`** (3.5) |
| 누가 | 사람이면 사용자 ID, AI면 에이전트 ID + 실행 ID + 실행시킨 사람, 엔진이면 엔진 이름 + 실행 ID |
| 언제 | 서버 UTC 시각 (컴퓨터 생성) |
| 무엇을 | 엔티티 유형과 ID |
| 어떤 행위 | CREATE / UPDATE / DELETE / LOGIN / LOGOUT / EXPORT / IMPORT / ENGINE_RUN |
| 이전 값 → 이후 값 | 변경된 필드 단위 |
| 사유 | 지정된 유형의 변경에 대해 **필수 입력** |
| 출처 | UI / IMPORT / API / ENGINE / AI |
| 승인 | AI 제안이 반영된 경우 승인자와 승인 시각 |

### 3.3 설계 규칙

**첫째, append-only.** 감사 로그는 수정도 삭제도 불가합니다. 애플리케이션 계정에 DB 수준에서 UPDATE/DELETE 권한을 주지 않습니다.

**둘째, 엔진 작업도 기록합니다.** 가정 변경으로 expected가 재생성되는 것은 대량의 데이터 변경입니다. 개별 행마다 로그를 남기면 폭증하므로, **엔진 실행 단위로 한 건**을 남기고 영향 범위(건수, 조건)를 기록합니다.

**셋째, 사유 입력을 선별적으로 요구합니다.** 모든 변경에 사유를 요구하면 사용자가 "수정"이라고만 적게 되어 의미가 없어집니다. 확정된 데이터의 정정, 항목 면제(`WAIVED`), 마일스톤 계획일 변경 등 **중요한 변경에만** 요구합니다.

**넷째, 조회 가능해야 합니다.** 기록만 하고 볼 수 없는 감사 추적은 요건을 만족하지 못합니다. 엔티티별 이력 보기와 관리자용 전역 검색을 모두 제공합니다.

### 3.5 행위자 구분 — 사람 / AI / 엔진 (검토 반영)

요구사항 10의 직접적 구현입니다. 감사 추적에서 **AI와 사람이 각각 무엇을 생성·수정·삭제했는지 명확히 구분**되어야 합니다.

| `actor_type` | 의미 | 재현 가능성 | 추가 기록 |
|---|---|---|---|
| `HUMAN` | 사람 사용자의 직접 조작 | — | 사용자 ID |
| `AI` | AI 에이전트의 행위 | 보장되지 않음 | 에이전트 ID, 작업 코드·버전, 실행 ID, 제공자·모델 식별자, 실행시킨 사람, 승인자 |
| `ENGINE` | 앱 내부 결정론적 엔진 | **완전 재현 가능** | 엔진 이름, 실행 ID, 트리거, 사용된 버전 좌표 |

`ENGINE`을 `AI`와 분리한 것이 중요합니다. Expectation Engine의 기대 항목 생성은 자동 처리이지만 AI가 아니며, 같은 입력에 같은 결과를 냅니다. 둘을 섞으면 **"AI가 만든 데이터"의 범위를 설명할 수 없게 되어** GCP와 computerised system validation 관점에서 문제가 됩니다.

상세 구조와 AI 실행 기록은 [14](14-ai-extensibility.md) 5장에 있습니다.

### 3.6 Part 11 격차 목록

지금 구현하지 않지만 **나중에 필요한 것**을 명시해 둡니다. 이것이 "대비 설계"의 실질입니다.

| 항목 | 현재 | validation 시 추가 |
|---|---|---|
| 감사 추적 스키마 | **구현** | 그대로 사용 |
| 행위자 구분 (사람/AI/엔진) | **구현** | 그대로 사용 |
| 전자 서명 (Part 11 Subpart C) | 미구현 | 서명 매니페스트, 재인증 |
| 시스템 검증 문서 (URS/FS/DS/IQ/OQ/PQ) | 미작성 | 작성 필요 |
| 변경 통제 절차 | 미수립 | 수립 필요 |
| 정기 감사 추적 검토 절차 | 미수립 | 수립 필요 |

## 4. 버전 관리 — 요구사항 C4

요구사항은 "사용자가 필요한 버전을 잘 구분할 수 있도록 정보에 버전이 있어야 한다"고 했습니다. 이 앱에서 버전이 붙는 대상은 **다섯 종류**이며, 각각 성격이 다릅니다.

| 대상 | 버전 성격 | 사용자에게 보이는 방식 |
|---|---|---|
| **데이터 스냅샷** | 시점 (as-of) | `스냅샷: 2026-09-14 08:00` |
| **가정 세트** | 개정 (revision) | `가정: v3 (2026-08-01 적용)` |
| **시험 설정** | 개정 (revision) | `설정: v2` — 유예 기간·단계 on/off ([13](13-trial-configuration.md)) |
| **지표 정의** | 개정 (revision) | `지표정의: v1` — 계산식 ([15](15-metric-specification.md)) |
| **Template / Mapping** | 개정 (revision) | Data Drop마다 기록 ([12](12-standard-source-templates.md) 6장) |

여기에 더해 각 Data Drop은 **출처(어느 vendor 데이터를 언제 추출해 누가 만든 파일인지)** 를 보유합니다. 표준화가 앱 밖에서 일어나므로 이 기록이 없으면 추적성이 끊깁니다.

검토 반영으로 **시험 설정과 지표 정의가 독립 버전으로 추가**되었습니다. 유예 기간 하나만 바뀌어도 모든 사이트의 overdue 건수가 바뀌므로, 설정은 지표 계산 좌표의 일부여야 합니다.

### 4.1 스냅샷

[06](06-logical-data-model.md) 3.2의 하이브리드 방식입니다. 일상 조회는 최신 상태를 보고, **공식 스냅샷**은 물리적으로 고정되어 언제든 그 시점의 화면을 재현합니다.

공식 스냅샷을 만드는 시점의 예시는 다음과 같습니다.

- 주간 리뷰 회의 직전 (정기)
- 마일스톤 도달 시점 (DBL, interim analysis)
- 사용자가 임의로 지정 (라벨 부여)

### 4.2 가정 세트

가정이 바뀌면 expected가 바뀌고, 따라서 **모든 과거 지표가 바뀝니다**. 이것이 혼란의 주된 원인이 되므로 다음 규칙을 둡니다.

**규칙 1.** 가정 세트는 개정할 때 새 버전을 만들고, 이전 버전은 보존합니다.

**규칙 2.** 각 스냅샷은 **어느 가정 버전과 어느 설정 버전, 어느 지표 정의 버전으로 계산되었는지** 기록합니다.

**규칙 3.** 과거 스냅샷은 **그 당시 가정으로 계산된 값을 유지**합니다. 새 가정으로 소급 재계산하지 않습니다. 다만 사용자가 명시적으로 "새 가정으로 재계산"을 선택하면 새 스냅샷이 생성됩니다.

규칙 3이 특히 중요합니다. 이것이 없으면 "왜 지난달 리포트의 숫자가 바뀌었나"라는 질문에 답할 수 없습니다.

### 4.3 화면 표시

모든 화면 상단에 현재 좌표를 항상 표시합니다.

```
  스냅샷: 2026-09-14 08:00 (공식) ▾   가정: v3 ▾   설정: v2 ▾   지표정의: v1 ▾

  분모 기준:  [● Due]  [ Protocol ]  [ Forecast ]        [비교 모드]
```

비교 모드에서 두 스냅샷의 **설정 버전이나 지표 정의 버전이 다르면 경고**가 표시됩니다. 유예 기간이 바뀐 상태로 두 시점을 비교하면 변화의 원인이 실적인지 설정인지 구분할 수 없기 때문입니다.

## 5. Import / Export — 요구사항 C5, C6

### 5.1 Import 파이프라인

```
① 템플릿 다운로드 → ② 파일 업로드 → ③ 형식 검증 → ④ 미리보기
                                                    ↓
   ⑦ 스냅샷 반영 ← ⑥ 확정(promote) ← ⑤ 검증 결과 확인
```

| 단계 | 개념 |
|---|---|
| ① 템플릿 | **표준 source dataset template** 제공 ([12](12-standard-source-templates.md)). 사내 표준 파일(external data reconciliation file 등)의 실제 구조에 맞춰 설계 |
| ② 업로드 | Data Drop 생성. 파일 해시로 중복 감지. **출처 메타데이터 필수** ([12](12-standard-source-templates.md) 2.2) |
| ③ 형식 검증 | 구조·완결성·무결성·일관성 4단계 점검 ([12](12-standard-source-templates.md) 5장) |
| ④ 미리보기 | 몇 건이 신규·변경·거부인지, 어떤 행이 왜 거부되는지 표시 |
| ⑤ 검증 결과 | 오류 리포트 다운로드 (원본 행 번호 포함) |
| ⑥ 확정 | 사용자가 명시적으로 승인해야 반영. **자동 반영하지 않음** |
| ⑦ 반영 | Progress Engine 실행, 감사 로그 기록 |

### 5.2 Mapping Profile

vendor마다 컬럼명과 코드값이 다릅니다. 매번 파일을 수정하게 하는 대신 **매핑을 앱에 저장**합니다.

```
MappingProfile:
  source_column "SUBJID"        → subject_no
  source_column "VISITNUM"      → visit_name  (코드 변환표 적용)
  source_column "COLLDT"        → collected_at (날짜 형식: DDMMMYYYY)
  코드 변환:  "1"→"Screening", "2"→"Baseline", ...
```

매핑 프로파일도 버전 관리하며, 각 Data Drop이 어느 프로파일로 처리되었는지 기록합니다. vendor가 리포트 형식을 바꾸면 새 버전을 만들고, 과거 Drop은 과거 프로파일을 유지합니다.

**이 장치가 표준 template의 부담을 실질적으로 없앱니다.** 매핑이 한 번 설정되면 사용자는 사내 표준 파일을 그대로 올릴 수 있고, 앱이 표준 형식으로 변환합니다. 표준 template은 목표 형식이지 업로드 필수 형식이 아닙니다.

앱의 입력 경계가 vendor 원본이 아니라 사내 표준 파일이므로(DP-12-6), 매핑이 흡수해야 할 차이는 그만큼 작아집니다. vendor 형식 변동은 표준화 단계에서 이미 흡수되기 때문입니다.

이 매핑 제안은 내부 LLM이 보조할 수 있습니다 ([14](14-ai-extensibility.md) 3.1).

### 5.3 재업로드와 멱등성

같은 기간 데이터를 여러 번 올리는 것은 정상입니다. 따라서 **키 기준 upsert**로 처리하며, 재업로드가 중복 행을 만들지 않도록 합니다. 다만 **이전 Data Drop 자체는 보존**됩니다.

### 5.4 Export — 세 가지 경로

요구사항 C6은 "앱에서 만들어진 데이터를 포함해 외부 시각화 도구의 소스로 쓸 수 있게 export"를 요구합니다. 세 경로를 제공합니다.

| 경로 | 형식 | 용도 |
|---|---|---|
| **화면 export** | CSV, Excel | 지금 보고 있는 테이블을 그대로 (원칙 4.7) |
| **분석용 데이터셋** | CSV, Parquet | [06](06-logical-data-model.md) ④층 `MetricFact` + 차원 테이블. **star schema 형태** |
| **읽기 전용 연결** | DB 뷰 또는 REST API | Power BI / Tableau / Spotfire 직접 연결 |

세 번째 경로가 가장 가치가 높습니다. 사용자가 파일을 내려받아 옮기는 대신 BI 도구가 직접 최신 데이터를 읽게 됩니다.

> **설계 주의.** Export 경로에도 권한과 눈가림 마스킹이 **반드시 동일하게** 적용되어야 합니다 (2.4 참조). 또한 모든 export는 감사 로그에 기록합니다.

### 5.5 내보내는 데이터셋 구조

BI 도구에서 바로 쓸 수 있도록 star schema로 제공합니다.

```
  dim_trial     dim_country    dim_site    dim_subject
  dim_visit     dim_activity   dim_stage   dim_date
       └───────────────┬───────────────────┘
                       ▼
              fact_stage_status      (항목·단계 수준 상세)
              fact_metric            (집계 수준, expected_basis 3종 포함)
              fact_issue             (쿼리·이슈, owner별 기한 포함)
              fact_discrepancy       (불일치, 유형·구간 포함)
              fact_validation        (업로드 검증 결과)
```

`fact_metric`에는 **Due / Protocol / Forecast 세 기준의 값이 모두 포함**되므로, 외부 BI 도구에서도 앱 화면과 동일한 기준 전환이 가능합니다.

모든 fact 테이블은 계산 좌표(스냅샷·가정·설정·지표정의 버전, 기준)를 컬럼으로 가집니다. 외부 도구에서도 **어느 조건의 숫자인지 추적 가능**해야 하기 때문입니다.

## 6. 지표 정의 등록부 (Metric Definition Registry)

벤치마크([01](01-benchmark.md) 2.2)에서 확인한 핵심 교훈에 대한 대응입니다. **정의가 불일치하면 숫자는 신뢰를 잃습니다.**

정식 명세와 전체 지표 목록은 [15](15-metric-specification.md)에 있습니다. 각 지표마다 다음을 데이터로 등록합니다.

| 항목 | 예시 |
|---|---|
| 코드 | `edc.entry.rate` |
| 표시명 | 데이터 입력률 |
| 정의문 | "due 상태가 된 폼 중 입력이 완료된 폼의 비율" |
| 분자 / 분모 | `completed(entered)` / `due(entered)` |
| 제외 조건 | 반복 폼 제외, 탈락 후 방문 제외, `WAIVED` 제외 |
| Due 규칙 | 방문일 + 14 달력일 (시험별 설정) |
| 임계값 | 경고 90%, 위험 80% (KRI용, [07](07-prediction-and-analytics.md) 5.2) |
| 버전 | v2 (2026-07-01 개정) |
| 처리 규칙 | 부분 날짜·결측·중복·반올림 처리 ([15](15-metric-specification.md) 3장) |

화면의 모든 지표 이름 옆에 `?` 아이콘을 두고 이 정의로 연결합니다. 회의에서 숫자를 두고 논쟁이 생기면 그 자리에서 정의를 확인할 수 있어야 합니다.

## 7. 동시성 (요구사항 C2의 "동시 접근")

여러 사용자가 동시에 같은 데이터를 수정할 수 있습니다.

| 상황 | 처리 |
|---|---|
| 같은 레코드 동시 수정 | **낙관적 잠금** — 저장 시 버전 충돌 감지, 사용자에게 알림 |
| 같은 Feed에 동시 업로드 | Data Drop은 각각 생성되되, promote는 순차 처리 |
| 엔진 실행 중 조회 | 조회는 항상 마지막 확정 상태를 봄. 계산 중 상태는 노출하지 않음 |
| 대량 편집 | 배치 작업으로 처리, 진행 상황 표시 |
