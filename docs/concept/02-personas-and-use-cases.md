# 02. 사용자와 활용 시나리오

## 1. 사용자 계층

요구사항에서 "시험 구성원뿐 아니라 매니저 레벨과 관련자에게도 도움이 되어야 한다"고 하셨습니다. 이 요구는 단순히 사용자를 늘리는 문제가 아니라, **계층별로 다른 질문에 답하는 서로 다른 화면**을 만들어야 한다는 뜻입니다.

| 계층 | 묻는 질문 | 필요한 화면 | 보는 주기 |
|---|---|---|---|
| L1 실무 | 오늘 내가 처리해야 할 항목은 무엇인가 | 작업 목록(worklist), 개별 항목까지 드릴다운 | 매일 |
| L2 시험 리드 | 우리 시험에서 어디가 위험한가 | 시험 단위 대시보드, 사이트 순위 | 주 1~2회 |
| L3 관리자·경영 | 여러 시험 중 무엇이 마일스톤을 놓칠 위험이 있는가 | 포트폴리오 뷰, 예외 신호만 | 월 1회 또는 보고 시 |

이 세 계층을 하나의 화면으로 만족시키려는 시도는 대부분 실패합니다. L3 사용자에게 필요한 것은 **더 적은 숫자**이지 더 요약된 같은 숫자가 아닙니다. 따라서 화면 설계에서 세 계층을 명시적으로 분리합니다 (→ [05](05-information-architecture.md)).

## 2. 페르소나

### 2.1 P1 — 임상 데이터 매니저 (CDM Lead)

주 업무는 EDC 데이터 품질과 DBL 준비입니다. 매주 입력률, 쿼리 적체, 코딩·리뷰 진척을 확인하고, DBL 전에는 남은 backlog가 기한 내 소진 가능한지 판단해야 합니다.

가장 큰 불편은 **분모를 매번 수작업으로 만드는 것**입니다. 어떤 피험자가 몇 차 방문까지 했는지를 RTSM에서 받아 SoA와 교차시켜 폼 수를 세는 작업을 매주 반복합니다.

- 주 사용 도메인: D1 (EDC), D2 (RTSM), D6 (Timeline)
- 필요한 권한: D1 write, D2 read, D6 read

### 2.2 P2 — 임상 시험 모니터 / CRA

담당 사이트의 방문 일정을 짜고 SDV를 수행합니다. 방문 전에 그 사이트에 SDV 대기 물량이 얼마나 쌓였는지 알아야 방문의 가치를 판단할 수 있습니다.

가장 큰 불편은 **방문 계획과 실제 부하가 따로 논다는 것**입니다. 분기 방문 계획은 미리 짜두었는데, 정작 방문 시점에 SDV 대상이 별로 없거나 반대로 감당 못 할 만큼 쌓여 있습니다.

- 주 사용 도메인: D3 (SDV plan), D1 (EDC의 SDV 부분), D2 (RTSM)
- 필요한 권한: D3 write, D1 read, D2 read

### 2.3 P3 — 임상 운영 리드 (Clinical Operations Lead)

등록 진척, 방문 준수, 사이트 성과를 총괄합니다. 방문 윈도우를 벗어난 방문은 프로토콜 일탈로 이어지므로 조기에 잡아야 합니다.

- 주 사용 도메인: D2 (RTSM), D3 (SDV), D6 (Timeline)
- 필요한 권한: D2 write, D3 read, D6 write

### 2.4 P4 — 바이오마커 / 검체 관리자

채취 예정 샘플이 실제로 채취되었는지, central lab에 도착했는지, bioanalytics lab으로 넘어갔는지, 분석되었는지를 추적합니다. 용혈 같은 샘플 이슈가 발생하면 데이터 대조나 분석 업무로 연결해야 합니다.

가장 큰 불편은 **여러 vendor 리포트를 각각 다른 형식으로 받아 수작업 대조**한다는 것입니다. 샘플 한 건이 어디서 멈췄는지 알려면 최소 3개 파일을 열어야 합니다.

- 주 사용 도메인: D4 (Sample)
- 필요한 권한: D4 write, D2 read

### 2.5 P5 — 영상 관리자 (Imaging Manager)

예상 영상이 사이트에서 획득되어 BICR에 업로드되었는지, QC를 통과했는지, 판독자에게 배정되어 판독이 완료되었는지를 추적합니다. investigator 평가와 BICR 평가 간 대상·시점 불일치도 확인해야 합니다.

- 주 사용 도메인: D5 (Image)
- 필요한 권한: D5 write, D2 read

### 2.6 P6 — 프로젝트 매니저 (PM)

마일스톤과 상세 task를 관리하며 여러 기능 팀의 진척을 취합합니다. 이 페르소나는 **다른 모든 도메인을 읽되 주로 D6에 쓰는** 특징이 있습니다.

- 주 사용 도메인: D6 (Timeline), 전 도메인 read
- 필요한 권한: D6 write, 전 도메인 read

### 2.7 P7 — 관리자·경영층 (Manager / Executive)

여러 시험을 동시에 봅니다. 상세 수치가 아니라 **예외 신호**가 필요합니다. "정상인 것은 보여주지 말고 문제만 보여달라"가 이 페르소나의 요구입니다.

- 주 사용 도메인: 포트폴리오 뷰
- 필요한 권한: 전 도메인 read (시험 범위 제한 가능)

### 2.8 P8 — 시스템 관리자 (System Admin)

사용자 계정, 역할, 권한, 시험 배정을 관리합니다. 업무 데이터는 다루지 않으며 **전용 관리 화면**만 사용합니다. 요구사항 C2가 명시한 역할입니다.

- 주 사용 도메인: Admin 모듈
- 필요한 권한: 사용자·역할·권한 관리 write, 업무 데이터는 기본 접근 없음

## 3. 페르소나별 권한 매트릭스 (초안)

이 매트릭스가 [08](08-platform-services.md)의 RBAC 설계로 이어집니다. `W`는 write, `R`은 read-only, `-`는 접근 없음입니다.

| 역할 | D1 EDC | D2 RTSM | D3 SDV | D4 Sample | D5 Image | D6 Timeline | Admin |
|---|---|---|---|---|---|---|---|
| P1 CDM Lead | W | R | R | R | R | R | - |
| P2 CRA | R | R | W | - | - | - | - |
| P3 ClinOps Lead | R | W | R | R | R | W | - |
| P4 Biomarker Mgr | R | R | - | W | - | R | - |
| P5 Imaging Mgr | R | R | - | - | W | R | - |
| P6 PM | R | R | R | R | R | W | - |
| P7 Manager | R | R | R | R | R | R | - |
| P8 System Admin | - | - | - | - | - | - | W |

여기에 **데이터 범위(data scope)** 가 직교로 곱해집니다. 같은 CRA 역할이라도 담당 국가나 사이트만 보도록 제한할 수 있어야 합니다 (→ [08](08-platform-services.md) 2장).

## 4. 핵심 활용 시나리오

시나리오는 개념이 실제로 작동하는지 검증하는 도구입니다. 아래 5개는 설계 검증용 기준 시나리오로 삼습니다.

### 4.1 UC-1. 주간 데이터 진척 리뷰 (P1)

CDM Lead가 월요일 아침에 시험 대시보드를 엽니다. 입력률이 지난주 91%에서 86%로 떨어진 것을 봅니다. 국가별로 펼치니 한 국가가 원인입니다. 그 국가의 사이트를 펼치니 신규 활성화된 사이트 두 곳에서 첫 피험자들의 폼이 통째로 밀려 있습니다. 사이트 화면에서 피험자별로 내려가 **어떤 방문의 어떤 폼**이 며칠째 밀렸는지 목록을 뽑아 사이트에 전달합니다.

이 시나리오가 검증하는 것: 4단계 드릴다운(원칙 4.3), 스냅샷 간 비교, 개별 항목 목록 export.

### 4.2 UC-2. SDV 방문 계획 적정성 검토 (P2)

CRA가 다음 분기 방문 계획을 세웁니다. 앱은 각 사이트에 대해 현재 SDV backlog와 예측 등록 추이를 바탕으로 방문 시점의 예상 SDV 물량을 계산합니다. 계획된 방문 횟수가 그 물량 대비 **부족/적정/과다** 중 어디인지 표시됩니다. CRA는 부족으로 표시된 두 사이트에 방문을 추가합니다.

이 시나리오가 검증하는 것: 예측 엔진과 계획의 결합, 리소스 평가 로직(요구사항 D3-e).

### 4.3 UC-3. 샘플 추적 (P4)

바이오마커 관리자가 "지난 30일 내 채취되었으나 bioanalytics lab에 도착하지 않은 샘플"을 조회합니다. 앱은 각 샘플이 **체인의 어느 단계에서 멈췄는지** 보여줍니다. 12건 중 8건은 central lab에 있고, 3건은 배송 중이며, 1건은 분실로 표시되어 있습니다. 분실 1건에 대해 이슈를 등록하고 데이터 대조 담당자에게 연결합니다.

이 시나리오가 검증하는 것: 단계 체인 모델(→ [03](03-core-concept-model.md) 3.3), 이슈 객체, 단계별 정체 분석.

### 4.4 UC-4. DBL 준비도 판단 (P1, P6)

DBL이 6주 앞입니다. PM이 Timeline 화면에서 DBL 마일스톤을 봅니다. 앱은 현재 backlog(미입력, 미SDV, 미코딩, 미서명, 미freeze)와 최근 소진 속도를 바탕으로 **현재 속도로는 DBL을 2주 초과한다**고 표시합니다. 어느 항목이 임계 경로인지도 함께 보여줍니다.

이 시나리오가 검증하는 것: 도메인 간 결합(D1 + D6), 소진율 기반 예측(→ [07](07-prediction-and-analytics.md)).

### 4.5 UC-5. 경영 보고 (P7)

매니저가 포트폴리오 화면을 엽니다. 8개 시험 중 3개가 빨간색입니다. 각각 무엇이 문제인지 한 줄로 요약되어 있습니다. 필요한 시험만 클릭해 들어가 상세를 봅니다. 회의용으로 이 데이터를 export하여 사내 Power BI 보고서에 연결합니다.

이 시나리오가 검증하는 것: 계층별 화면 분리(1장), 외부 BI 연동(요구사항 C6).

## 5. 검토 포인트 (Decision Points)

| # | 결정 필요 사항 | 기본 제안 |
|---|---|---|
| DP-02-1 | 페르소나 목록에 빠진 역할이 있는가 (예: Medical Monitor, Biostatistician, Site 사용자) | 현 8개로 시작 |
| DP-02-2 | **사이트 직원이 이 앱에 직접 접근하는가** — 접근한다면 보안·권한 설계가 크게 달라짐 | **접근하지 않음** (내부 sponsor/CRO 전용)으로 전제 |
| DP-02-3 | 3장 권한 매트릭스의 기본값이 실제 조직과 맞는가 | 실무 검토 필요 |
| DP-02-4 | 역할을 고정 세트로 제공할 것인가, 관리자가 자유롭게 정의하게 할 것인가 | **자유 정의 + 기본 템플릿 제공** |
